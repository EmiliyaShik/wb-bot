# ТЗ: WBРентген (@WBRentgen_bot), платформа платных агентов аналитики Wildberries

## Что это
Бот позволяет средним селлерам Wildberries подключить свой кабинет и платить только за нужные модули: финансы, план-факт, реклама, воронка. Бот сам собирает данные и присылает готовые разборы: куда уходят деньги, где выросли скрытые расходы, какие артикулы прибыльны, как магазин идёт к плану. Цель: убрать ручной сбор таблиц и показать утечки, которые снижают чистую прибыль.

## Кто пользуется
- Клиенты: селлеры WB (как правило ИП и ООО). Каждый видит только свой кабинет.
- Владелец бота: администратор. Видит клиентов, счета, оплаты, ошибки, расходы. Выдаёт и отменяет доступ, перезапускает задачи.
- Продавец услуги: российский ИП. Его реквизиты указываются в счетах и оферте. Сам ИП ботом пользуется только в рамках своего кабинета на Wildberries, на нем и проводится тестирования бота, владелец передаёт ему данные для актов.

## Принцип устройства
- Все агенты этапов 0-2 это обычный код на Python: запрос к WB API, расчёт по формулам, сообщение или Excel. Нейросеть в них не используется.
- Нейросеть подключается только на этапе 3 и только там, где это прямо указано.
- Каждый агент это отдельный модуль кода. Общие части переиспользуются всеми агентами: клиент WB API, хранилище, очередь задач, проверка доступа к модулю.

## Этап 0. Фундамент

0.1 Доступ к WB API
- Проверить запросы к *-api.wildberries.ru напрямую с Bothost без прокси. Если не работает, выяснить причину (403, гео, заголовок Authorization) и доложить владельцу до продолжения работ.
- Клиенты подключаются персональным токеном WB (решение владельца).
- Меры для токенов:
  - бот просит создать ОТДЕЛЬНЫЙ токен только для WBРентгена, чтобы клиент мог отозвать его, не ломая другие интеграции;
  - токен только на чтение;
  - только категории Статистика, Аналитика, Продвижение, Контент;
  - токен хранится только в зашифрованном виде.
- Перед подключением клиент нажимает кнопку согласия с офертой (ссылка на оферту в конфиге). Факт и время согласия сохраняются.
- Код подключения сделать так, чтобы позже можно было добавить сервисный токен и OAuth 2.0 WB без переделки агентов.

0.2 Подключение кабинета
- /connect: бот по шагам объясняет, как создать персональный токен только на чтение с нужными категориями.
- Проверка токена: срок действия, категории, пробный запрос. Если прав не хватает, бот называет, чего именно и какие модули без этого не заработают.
- Напоминания за 14 и за 3 дня до окончания срока токена.
- Если WB вернул 401 (токен отозван или просрочен), бот сообщает клиенту и ставит модули на паузу. Оплаченные дни доступа за время паузы не сгорают.
- Один клиент подключает один кабинет.
- /disconnect удаляет токен и все данные клиента (с подтверждением кнопкой).

0.3 Себестоимость
- Бот выдаёт Excel-шаблон, заполненный артикулами клиента из Content API: nmId, артикул продавца, название, пустая колонка «себестоимость за единицу».
- Клиент присылает файл обратно, бот проверяет и сохраняет.
- Артикулы без себестоимости помечаются в отчётах «нет себестоимости», прибыль по ним не считается.

0.4 Очередь фоновых задач
- Тяжёлые выгрузки идут в фоне с соблюдением лимитов WB API (у отчёта о реализации лимит особенно строгий, проверить актуальный). Клиенту сразу приходит «принято, пришлю, когда будет готово», потом результат.
- Ошибка 429: подождать и повторить.
- Ошибка 401: сообщить клиенту про токен (см. 0.2).
- WB недоступен: повторить позже. После нескольких неудач сообщить клиенту понятным текстом и записать ошибку для владельца.

0.5 Расписание
- Ежедневные отчёты утром, еженедельные после появления нового финотчёта WB. Время по умолчанию московское.
- Клиент может отключить рассылки в /settings.

0.6 Хранилище
- Одна база в /app/data, данные строго разделены по клиенту.
- Хранить недельные строки финотчёта и суточные данные по артикулам, чтобы строить динамику без повторных запросов к WB.

0.7 Учёт расходов и выручки
- По каждому клиенту за месяц считать:
  - число вызовов WB API по методам;
  - токены нейросети и их стоимость (этап 3);
  - счета и оплаты.
- Админ-команда /stats: активные клиенты по модулям, выручка за месяц, расходы, маржа по клиентам, выставленные и неоплаченные счета.

## Этап 1. Модули, тарифы, оплата

1.1 Модули и цены (все цены и периоды в конфиге, не в коде)
- diagnostic: бесплатная диагностика. Разовый срез прошлой недели и 3 главные утечки в рублях; в конце подсказки, какой модуль что найдёт. Одна диагностика на один кабинет WB (по ID продавца), а не на Telegram-аккаунт.
- finance: 990 ₽ в месяц (агенты 1, 2, 3).
- rnp: 590 ₽ в месяц (агент 4).
- ads: 1 290 ₽ в месяц (агенты 5, 6). Скрыт до этапа 3.
- funnel: 490 ₽ в месяц (агент 7). Скрыт до этапа 3.
- all: 2 290 ₽ в месяц, все доступные модули.
- Периоды: 1 месяц; 3 месяца со скидкой 10%; 12 месяцев со скидкой 20%.
- Пробный период 7 дней на один модуль по выбору, один раз на кабинет WB.

1.2 Общая логика доступа
- Любой способ оплаты в итоге вызывает одну функцию: «продлить модуль X клиенту Y на N дней по платежу Z». Повторный вызов с тем же платежом ничего не продлевает.
- /tariffs показывает модули, цены, что входит в каждый и текущий статус клиента.
- Команда модуля без доступа отвечает: что даёт модуль, цена, кнопка «Оформить».
- После включения клиенту приходит сообщение: модуль подключён до такой-то даты.
- За 5 дней до конца срока бот предлагает продлить (выставить счёт).
- После окончания срока 3 дня льготного периода, затем модуль выключается.
- Данные клиента хранятся ещё 30 дней после выключения всех модулей, затем удаляются (с предупреждением за 3 дня).
- Команда /paysupport: как связаться с владельцем по вопросам оплаты.
- Админ-команды владельца:
  - выдать доступ вручную с указанием способа оплаты (счёт, карта, другое) и номера платежа;
  - отменить доступ (возврат).
  Всё пишется в журнал.

1.3 Оплата по счёту (основной способ в v1)
- Клиент выбирает модуль и период, бот спрашивает ИНН.
- Бот проверяет ИНН и подтягивает название и адрес через открытый сервис проверки контрагентов (подобрать бесплатный или недорогой, согласовать с владельцем). Если не получилось, клиент вводит реквизиты вручную.
- Бот формирует счёт в PDF с уникальным номером.
  - Реквизиты ИП-продавца и ссылка на оферту берутся из переменных окружения и конфига, в коде их нет.
  - Номер счёта указывается в назначении платежа.
  - Наименование услуги: «Предоставление доступа к онлайн-сервису WBРентген, модуль ..., период ...» (формулировку вынести в конфиг, владелец согласует с бухгалтером).
- Счёт действует 5 банковских дней. Статусы: выставлен, оплачен, просрочен, отменён.
- Владелец получает уведомление о каждом новом счёте. После проверки выписки нажимает «Оплачен», доступ включается автоматически, клиенту приходит сообщение.
- Раз в месяц (и по команде /acts) бот присылает владельцу Excel оплаченных счетов для подготовки актов: номер, дата, ИНН, название клиента, модуль, период, сумма.
- Отложено: автоматическая сверка поступлений через API банка ИП. Изучить, какой банк у ИП, и описать владельцу, что для этого понадобится.

1.4 Оплата картой (вне автоматизации в v1)
- Если клиент хочет платить картой или по СБП, бот показывает контакт владельца.
- Владелец принимает оплату по платёжной ссылке банка ИП, чек выбивается на кассе ИП, затем владелец выдаёт доступ админ-командой из 1.2 со способом «карта».
- Боту ничего не нужно знать о кассе.

1.5 Tribute (ОТЛОЖЕНО, делать только по отдельной команде владельца)
- Перед реализацией изучить справку wiki.tribute.tg: «Интеграция цифровых товаров в свой продукт», «Вебхуки», «API Магазина», «Онлайн-касса».
- Доложить владельцу:
  - какой вариант подходит (цифровые товары или заказы Магазина);
  - в какой валюте приходят выплаты;
  - как устроены чеки.
- Реализация:
  - для каждой пары «модуль + период» свой товар в рублях, соответствие ID товара, модуля и дней в конфиге;
  - вебхук принимать только с проверкой подписи trbt-signature (HMAC-SHA256 на API-ключе Tribute);
  - повторная доставка того же платежа ничего не продлевает;
  - событие возврата выключает модуль;
  - нужен HTTPS-адрес для вебхука: выяснить, как сделать это на Bothost, и провести владельца по шагам.

## Этап 2. Агенты модулей finance и rnp (только код)

Агент 1. Финансист (модуль finance)
- Источник: Statistics API, детализация отчёта о реализации (reportDetailByPeriod; сверить версию, поля и лимиты).
- /finance: кнопки периода (последняя неделя, месяц, квартал, год).
- Раскладка по неделям:
  - продажи, возвраты, к перечислению;
  - комиссия WB, эквайринг (в рублях и в процентах);
  - логистика, хранение, приёмка, штрафы;
  - прочие удержания (в том числе за рекламу);
  - СПП.
- Результат: короткая сводка в сообщении и Excel с листами «Недели», «Месяцы» (свод недель в месяц), «По артикулам», «Методология» (какие поля и формулы использованы).
- Поля и формулы записать в CLAUDE.md.
- Повторная выгрузка той же недели заменяет данные, а не дублирует.

Агент 2. Сторож скрытых расходов (модуль finance)
- Работает на данных агента 1, новых запросов к WB не делает.
- Каждую неделю считает:
  - фактическую комиссию площадки в процентах от продаж (реально удержанную, а не тарифную);
  - эквайринг в процентах;
  - средний процент СПП;
  - долю логистики и долю хранения в выручке.
- Сравнивает со средним за 4 предыдущие недели.
- Пороги алерта (в конфиге):
  - эквайринг +0,5 п.п.;
  - фактическая комиссия +2 п.п.;
  - СПП -5 п.п.;
  - доля логистики или хранения +2 п.п.
- Алерт по шаблону: что изменилось, на сколько, сколько рублей это стоило за неделю при текущей выручке.
- /dynamics: таблица этих показателей по неделям за выбранный период.

Агент 3. Прибыльность артикулов (модуль finance)
- Источники: данные агента 1, себестоимость из 0.3, расход рекламы по артикулам из Promotion API (fullstats; сверить версию).
- По каждому артикулу за период:
  - выручка, штуки, себестоимость;
  - комиссия, эквайринг, логистика, хранение, штрафы, реклама, возвраты;
  - чистая прибыль, маржинальность, доля в общей прибыли.
- Сортировка от самых прибыльных к убыточным. Отдельный блок «убыточные, обезличка, без себестоимости».
- /profit: топ-5 и антитоп-5 в сообщении плюс Excel.

Агент 4. РНП, план-факт (модуль rnp)
- /plan: план на месяц по выручке и заказам.
- Источники: воронка продаж по дням (Analytics API, сверить метод), остатки, расход рекламы.
- Ежедневный утренний отчёт:
  - заказы и выручка за вчера против среднего за 7 дней;
  - факт с начала месяца, процент выполнения плана, прогноз на конец месяца по текущему темпу;
  - расход на рекламу и ДРР за вчера;
  - артикулы, у которых остатка хватит меньше чем на 14 дней при текущей скорости продаж.
- Если план не задан, отчёт приходит без блока план-факт.

## Этап 3 (только по отдельной команде владельца)

Агент 5. Рекламный отчёт (модуль ads), код
- Расход, заказы, CPO, ДРР по каждой кампании и по дням против целевого ДРР клиента (по умолчанию 15%, меняется в /settings).
- Источники: /adv/v1/promotion/count, fullstats (сверить версии).

Агент 6. Минус-кластеры (модуль ads), код
- Сначала проверить в документации, отдаёт ли статистика поисковых кластеров (normquery) заказы.
- Если заказов там нет, отбирать кластеры по правилу «высокий расход и CTR ниже половины среднего по кампании». Клиенту честно писать, что это оценка без данных о заказах.
- Добавление в минус только если клиент отдельно подключил токен с правом записи в категории Продвижение. Действие выполняется только по кнопке «Подтвердить» с понятным описанием, все действия пишутся в журнал.

Агент 7. Диагност воронки (модуль funnel), код плюс опционально нейросеть
- Конверсии по артикулу: показы в переходы, переходы в корзину, корзина в заказ, заказ в выкуп.
- Сравнение с прошлым периодом, поиск этапа с просадкой, типовая подсказка по правилам:
  - просел CTR: главное фото и цена;
  - просела корзина: контент и возражения в карточке;
  - просел выкуп: отзывы, размеры, качество.
- Опционально объяснение простым языком через Claude Haiku 4.5 с жёстким лимитом токенов.

Агент 8. Адвокат клиента (разовая платная услуга), нейросеть и парсинг
- Делать отдельным ТЗ после приёмки этапов 0-2.
- Ориентир себестоимости: не больше 80 ₽ за прогон. Жёсткий лимит токенов и страниц на прогон.

## Ограничения
- Репозиторий публичный: в коде и истории коммитов не должно быть секретов, реквизитов ИП, ID клиентов, базы и выгрузок.
- Бот не меняет ничего в кабинете клиента без подтверждения кнопкой.
- Один клиент никогда не видит данные другого.
- Бот не ведёт налоговый и кассовый учёт: только выставляет счета и отдаёт владельцу реестр оплат.
- Тексты бота на русском языке, без длинных тире (использовать дефис, запятую или перестраивать фразу).
- Не превышать лимиты WB API: лучше медленнее, чем блокировка токена.

## Как проверить, что готово
- Если клиент прислал рабочий токен с нужными категориями и согласился с офертой, придёт подтверждение и список модулей со статусами.
- Если токен неверный, просроченный или без нужных категорий, бот объяснит, что не так и как исправить.
- Если клиент не нажал согласие с офертой, токен не принимается.
- Если клиент прошёл диагностику, он получит 3 утечки в рублях. Повторная диагностика того же кабинета с другого Telegram-аккаунта не выдаётся.
- Если клиент выбрал finance на 3 месяца и ввёл ИНН, придёт PDF-счёт с правильной суммой со скидкой и реквизитами ИП.
- Если клиент ввёл неверный ИНН, бот попросит исправить.
- Если владелец нажал «Оплачен», модуль включится ровно на оплаченный период. Повторное нажатие по тому же счёту ничего не продлит.
- Если счёт не оплачен 5 банковских дней, он станет просроченным, клиенту придёт напоминание.
- Если без доступа вызвать /profit, бот покажет описание модуля и кнопку «Оформить».
- Если срок доступа истёк, через 3 дня модуль выключится, данные останутся на 30 дней.
- Если WB вернул 401, модули встанут на паузу, а оплаченные дни не сгорят.
- Если запросить /finance за год, сначала придёт «принято», потом Excel. Цифры любой недели совпадают с отчётом в личном кабинете WB.
- Если эквайринг вырос выше порога, в еженедельной рассылке придёт алерт с суммой в рублях.
- Если себестоимость не загружена, /profit работает и помечает такие артикулы.
- Если план не задан, РНП приходит без блока план-факт и не падает.
- Если WB API недоступен или вернул 429, бот не падает и сообщает понятным текстом.
- Если неподключённый пользователь пишет боту, он получает вежливое объяснение, как начать.
- /acts выдаёт владельцу Excel оплаченных счетов за месяц.
- /stats показывает клиентов, выручку, расходы и маржу.
- После /disconnect токен и данные клиента удалены.
- В репозитории и его истории нет секретов, реквизитов и данных клиентов.

## Безопасность, применить по умолчанию
- Секреты и реквизиты ИП только в переменных окружения Bothost и локальном .env. Файл .env в .gitignore, рядом .env.example с заглушками.
- Проверить историю публичного репозитория на ранее утёкшие ключи. Если есть, сказать владельцу, что перевыпустить.
- Токены клиентов шифровать, ключ шифрования только в переменных окружения.
- База, счета и выгрузки в .gitignore, никогда не коммитятся.
- Админ-команды доступны только владельцу по Telegram ID из переменной окружения.
- Ограничение частоты команд на одного клиента.
- Принимаемые файлы: только xlsx, лимит размера, проверка содержимого.
- Нейросеть (этап 3): лимит токенов на запрос и на клиента в месяц, понятное сообщение при исчерпании. Напомнить владельцу выставить лимит трат в консоли Anthropic.
- Tribute (если будет включён): проверка подписи вебхука, запрет повторной обработки платежа, API-ключ только в переменных окружения.
- В логи писать события, не токены, не реквизиты и не данные клиентов.
- Любая запись в кабинет WB только с отдельным токеном, по подтверждению, с журналом.
