# Спецификация: WBРентген (@WBRentgen_bot)

Версия 1. Основана на `2026-09-15-brief.md` и ответах брифинга от 2026-09-15.

## Задача

Селлер Wildberries видит в личном кабинете кучу цифр, но не видит главного: сколько он на самом деле заработал и куда утекли деньги. Чтобы это понять, он раз в неделю выгружает отчёт о реализации, открывает Excel, руками сводит комиссию, логистику, хранение, штрафы, рекламу и себестоимость, и только тогда узнаёт, что эквайринг тихо вырос на полпроцента, а два артикула из топа продаются в минус. На это уходит несколько часов, поэтому чаще всего он этого не делает вообще и живёт по выручке, а не по прибыли.

## Решение

Телеграм-бот, которому селлер один раз отдаёт токен своего кабинета WB (только на чтение) и дальше получает готовые разборы: еженедельную финансовую раскладку, алерты о выросших скрытых расходах, прибыльность по каждому артикулу и ежедневный план-факт. Платит только за те модули, которые ему нужны. Счета выставляет сам бот, доступ включает владелец одной кнопкой после проверки выписки.

Существующая функция бота (пришли артикул - получи карточку товара с витрины WB) остаётся и работает без подключения кабинета.

## Решения по реализации

### Стек

| Что | Чем | Почему |
|---|---|---|
| Язык | Python 3.13 | уже в проекте (`.python-version`) |
| Телеграм | `python-telegram-bot` 21.x | уже в проекте, в нём же `JobQueue` для расписания |
| HTTP | `httpx` (async) | уже в проекте |
| База | SQLite через `sqlite3` из стандартной библиотеки | одна база в файле, ноль внешних сервисов. На Bothost один контейнер, СУБД ставить некуда и незачем |
| Конфиг | `config.toml` + `tomllib` из стандартной библиотеки | цены и периоды в файле, а не в коде. `tomllib` есть в Python с 3.11, зависимость не нужна |
| Excel | `openpyxl` | самый простой способ писать xlsx и читать присланный файл |
| PDF | `reportlab` | чистый Python. Альтернативы (weasyprint, wkhtmltopdf) тянут системные библиотеки, которых в slim-образе нет |
| Шифрование | `cryptography` (Fernet) | стандарт де-факто, симметричный ключ из переменной окружения |
| Расписание | `JobQueue` из python-telegram-bot | это APScheduler внутри процесса бота. Отдельный планировщик - лишний процесс |
| Часовые пояса | `tzdata` | **D01:** на Windows базы часовых поясов в системе нет, и `ZoneInfo("Europe/Moscow")` падает. Пакет чистый Python, без сборки. Добавлен после таска 03 |
| Тесты | `pytest` + `pytest-asyncio` | без них нельзя подтвердить «существующие функции не ломать» |

Новые зависимости: `openpyxl`, `reportlab`, `cryptography`, `python-telegram-bot[job-queue]`, `pytest`, `pytest-asyncio`. Прокси-поддержка `httpx[socks]` остаётся как есть.

### Хранилище

Одна база `${DATA_DIR}/wbrentgen.db`, по умолчанию `DATA_DIR=/app/data` (подтверждено по документации Bothost: всё в `/app` вне `/app/data` затирается при деплое). Локально - `./data`.

Режим `WAL`, `foreign_keys=ON`. Схема версионируется: таблица `schema_version` и пронумерованные миграции `migrations/001_*.sql`, применяются при старте по возрастанию. Откат не поддерживается: только вперёд.

Таблицы (перечень, не DDL):

- `clients` - telegram_id, seller_id (из токена WB), created_at, settings (JSON), paused_since
- `consents` - client_id, offer_url, offer_version, agreed_at
- `wb_tokens` - client_id, ciphertext, exp, scopes, last_ok_at, last_401_at
- `module_access` - client_id, module, until, source (trial / invoice / manual), state (active / grace / paused / off)
- `access_log` - client_id, module, action, days, payment_ref, method, actor, at
- `invoices` - number, client_id, inn, org_name, org_address, module, period_months, amount, status, issued_at, due_at, paid_at
- `invoice_seq` - год, последний номер
- `costs` - client_id, nm_id, cost_per_unit, updated_at
- `fin_weeks` - client_id, report_id, date_from, date_to + агрегаты недели и агрегат-сверка из `sales-reports/list`
- `fin_rows` - client_id, report_id, rrd_id + строки отчёта в исходных именах WB (сырьё для пересчётов)
- `nm_daily` - client_id, date, nm_id + суточные метрики (заказы, выручка, воронка, остаток, расход рекламы)
- `plans` - client_id, year_month, revenue_target, orders_target
- `diagnostics` - seller_id, done_at (привязка к кабинету, а не к Telegram)
- `trials` - seller_id, module, started_at (тоже к кабинету)
- `tasks` - очередь: id, client_id, kind, payload, state, attempts, next_run_at, created_at, finished_at
- `api_calls` - client_id, host, method, status, at (для `/stats` и лимитов)
- `events` - журнал: at, level, client_id, kind, message

**Изоляция клиентов.** Каждая таблица с данными клиента имеет `client_id`, и весь доступ идёт через слой репозитория, который принимает `client_id` первым аргументом. Функции без `client_id` в этом слое не существует - это и есть гарантия, что один клиент не увидит другого.

### Клиент WB API

Один модуль `core/wbapi`, единственное место в проекте, которое знает про HTTP и токены.

**Все эндпоинты, поля и лимиты сверены с официальной документацией 15.09.2026** и записаны в `.autopilot/<прогон>/wb-api-facts.md`. Таск 02 переносит их в `docs/wb-api.md`. Ничего, помеченного там «НЕ ПОДТВЕРЖДЕНО», в код не попадает.

**Четыре метода из ТЗ Wildberries отключил или убрал из документации, используются замены:**

| Из ТЗ | Статус | Что вместо |
|---|---|---|
| `GET /api/v5/supplier/reportDetailByPeriod` | отключён 15.07.2026 | `POST finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed` |
| `GET /api/v1/supplier/stocks` | отключён 23.06.2026 | `POST seller-analytics-api.wildberries.ru/api/analytics/v1/stocks-report/wb-warehouses` |
| `POST /api/v2/nm-report/detail` | нет в документации | `POST seller-analytics-api.wildberries.ru/api/analytics/v3/sales-funnel/products` |
| `POST /adv/v2/fullstats` | нет в документации | `GET advert-api.wildberries.ru/adv/v3/fullstats` |

**Авторизация.** Заголовок `Authorization: <токен>`, **без** `Bearer`.

**Проверка токена - без единого запроса к WB.** Токен это JWT со сроком 180 дней. Из payload читаются: `exp` (срок), `sid` (UUID кабинета - им же ключуются диагностика и пробный период), `acc` (тип токена, `3` - персональный), маска `s`. Бит категории: Контент 1, Аналитика 2, Статистика 5, Продвижение 6, Финансы 13. **Бит 30 - «только на чтение»**, им проверяется требование ТЗ. Один сетевой запрос делается только чтобы убедиться, что токен не отозван.

**Лимиты (из документации, на персональный токен):**

| Метод | Лимит |
|---|---|
| `sales-reports/detailed` и `/list` | **1 запрос в минуту** - самый жёсткий в проекте |
| `adv/v3/fullstats` | 3 запроса в минуту, максимум 50 кампаний и 31 день за раз |
| воронка продаж и остатки | 3 запроса в минуту |
| `content/v2/get/cards/list` | 100 запросов в минуту |
| `/ping` | **3 запроса за 30 секунд на домен**, автоматизировать запрещено: только по команде `/diag`, с паузами |

Ограничитель частоты: token bucket на токен и на метод. **Сами лимиты живут в коде, рядом с таблицей эндпоинтов, а не в `config.toml`** - решение принято после таска 02: это факты про WB, а не настройки владельца, и вынос их в конфиг приглашает поднять лимит, чего требование R150 прямо не хочет («лучше медленнее, чем блокировка токена»). В конфиге остаётся только лимит `/ping`. Число попыток и растущая пауза, наоборот, настройка: они читаются из секции `[queue]`, одной и той же для транспорта и для очереди, чтобы два слоя повторов не перемножались. У отчёта о реализации отдельная медленная дорожка. При 429 пауза берётся из заголовка `X-Ratelimit-Retry` (секунды); `X-Ratelimit-Remaining` читается во всех остальных ответах, чтобы не упираться в лимит вслепую.

**Ошибки переводятся в свои классы, и 401 с 403 не смешиваются:**

- `WBAuthError` (401) - проблема с самим токеном: отозван, просрочен, повреждён. Это пауза модулей по ТЗ.
- `WBForbiddenError` (403) - токен валиден, но нет прав: не та категория, попытка записи read-only токеном. **Не пауза**: бот называет недостающую категорию.
- `WBRateLimited` (429), `WBUnavailable` (5xx, таймаут), `WBApiError`.

Каждый вызов пишет строку в `api_calls`. Агенты получают клиент через `get_wb_client(client_id)` и **никогда не видят сам токен** - это то, что позволит позже подставить сервисный токен или OAuth, не трогая агентов.

### Деньги

**В базе деньги хранятся целыми копейками** (колонки с суффиксом `_kop`, тип `INTEGER`), в расчётах поднимаются в `Decimal`, `float` в денежном пути не используется нигде. Проценты и доли остаются `REAL`.

Решение принято в таске 01 после ревью: дробные числа не складываются до копейки, и в финансовом отчёте это вылезло бы расхождением с кабинетом WB - тем самым, которого требование R165 прямо не допускает. Отменить его позже нельзя дешёво: схему базы менять в этой сборке запрещено по конструкции, и вторая миграция потребовала бы переписать все агрегаты.

### Неполные и несверенные недели

Неделя может оказаться **неполной** (выгрузка упёрлась в потолок страниц) или **несверенной** (WB не отдал контрольный агрегат). Эти два состояния не смешиваются и обрабатываются агентами **по-разному, намеренно**:

| Агент | Неполная неделя | Почему |
|---|---|---|
| Сторож скрытых расходов | **исключается** из сравнения | занижённая выручка дала бы ложную тревогу, а сторож для того и нужен, чтобы тревога значила что-то |
| Прибыльность артикулов | **считается**, помечена датами | исключение оставило бы селлера вообще без ответа, а неточная цифра с честной пометкой лучше молчания |

Несверенная неделя считается у обоих, но с оговоркой в тексте. Три состояния (сошлось, разошлось, сверка не выполнена) различимы и в Excel, и в сводке.

### Очередь фоновых задач

Таблица `tasks` плюс один asyncio-воркер в процессе бота.

- Постановка задачи → клиенту сразу «принято, пришлю, когда будет готово».
- Воркер берёт задачи по `next_run_at`, соблюдая лимиты WB.
- 429 → пауза и повтор. 401 → задача отменяется, клиенту про токен, модули на паузу. 5xx и таймаут → повтор с растущей паузой; после N попыток (конфиг) - понятное сообщение клиенту и запись ошибки владельцу.
- Задачи переживают перезапуск: состояние в базе, при старте всё `running` возвращается в `pending`.

### Доступ к модулям

Одна функция - единственная дверь, через которую включается доступ:

```
grant_access(client_id, module, days, payment_ref, method, actor) -> Access
```

`payment_ref` уникален. Повтор с тем же `payment_ref` не продлевает ничего, возвращает уже выданный доступ и пишет в журнал строку «дубль». Так устроены все пути: счёт, пробный период, ручная выдача владельцем, и так же будет устроен Tribute, если его когда-нибудь включат.

Состояния доступа: `active` → (срок вышел) `grace` 3 дня → `off`. Отдельно `paused` при 401: пауза не тратит оплаченные дни, при восстановлении токена срок сдвигается на длительность паузы.

### Счета

Номер: `WBR-{ГГГГ}-{NNNN}`, счётчик в таблице, сквозной в пределах года, не повторяется после перезапуска. Тот же номер идёт в назначение платежа.

Срок: 5 банковских дней. Банковский день - будний день, исключая список праздников из конфига (по умолчанию список пуст, и тогда это просто будни). Производственный календарь РФ как зависимость не тянем: он меняется раз в год и его проще дописать в конфиг.

PDF собирается `reportlab`: шапка с реквизитами ИП из переменных окружения, таблица с одной строкой услуги, сумма, назначение платежа, ссылка на оферту. Строка про НДС берётся из конфига (`invoice.vat_note`) и по умолчанию **пустая**: налоговый режим ИП это факт о продавце, а не догадка. Пока строка пуста, бот при формировании первого счёта пишет владельцу, что её надо заполнить.

### Проверка ИНН

Адаптер `core/billing/counterparty.py` с одной функцией `lookup(inn) -> Counterparty | None`.

- Контрольная сумма ИНН (10 и 12 знаков) считается локально, без сети. Неверная - сразу «проверь цифры».
- Если `DADATA_API_KEY` задан - запрос в DaData за наименованием и адресом.
- Ключа нет, сервис недоступен, ничего не нашлось - возвращается `None`, и клиент вводит реквизиты руками. Это не ошибка, это штатная ветка.

### Внешние сервисы и переменные окружения

| Переменная | Что | Обязательна |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота | да |
| `ENCRYPTION_KEY` | ключ Fernet для токенов клиентов | да, иначе бот не принимает токены и честно об этом пишет |
| `ADMIN_TELEGRAM_IDS` | ID владельца через запятую | нет, но без неё админ-команд нет ни у кого |
| `DATA_DIR` | папка данных, по умолчанию `/app/data` | нет |
| `SELLER_NAME`, `SELLER_INN`, `SELLER_OGRNIP`, `SELLER_ADDRESS`, `SELLER_ACCOUNT`, `SELLER_BANK`, `SELLER_BIK`, `SELLER_CORR_ACCOUNT` | реквизиты ИП для счёта | нет; пока пусты - счёт не выставляется, бот объясняет владельцу, чего не хватает |
| `OFFER_URL` | ссылка на оферту | нет; пока пуста - кнопка согласия показывает предупреждение владельцу в логе, клиенту говорит «оферта готовится» |
| `OWNER_CONTACT` | контакт для `/paysupport` и оплаты картой | нет |
| `DADATA_API_KEY` | ключ DaData | нет; без него реквизиты руками |
| `WB_PROXY_ENABLED`, `WB_PROXY` | как сейчас | нет |

Все они попадают в `.env.example` с пустыми значениями. В коде реальных значений нет и не будет.

### Что остаётся от старого бота

`wb_api.py` (витрина WB: карточка, отзывы, характеристики) и обработчик артикула переезжают в `legacy/` без изменения логики и продолжают работать для всех, включая неподключённых. Это отдельный мир: витрина `card.wb.ru` не имеет отношения к API продавца `*-api.wildberries.ru`, у них разные хосты, разная авторизация и разные правила.

| `core.metering` | учётом вызовов и денег | `record_call(...)`, `stats(period)` | агрегацию |
| `core.audit` | журналом | `log(kind, client_id, message)` | фильтрацию секретов |
| `agents.finance` | недельной финансовой раскладкой | `build(client_id, period) -> FinanceReport` | поля WB, формулы, дедупликацию недель |
| `agents.watchdog` | поиском выросших расходов | `check(client_id) -> list[Alert]`, `dynamics(client_id, period)` | пороги, сравнение с 4 неделями |
| `agents.profit` | прибыльностью артикулов | `build(client_id, period) -> ProfitReport` | разнесение расходов по артикулам |
| `agents.rnp` | планом-фактом | `daily(client_id) -> RnpReport` | прогноз, расчёт дней остатка |
| `agents.diagnostic` | бесплатной диагностикой | `run(seller_id, client_id) -> Diagnostic` | выбор трёх утечек |
| `bot.*` | телеграм-поверхностью | хендлеры команд | тексты, клавиатуры, форматирование |
| `legacy.card` | витриной WB (старая функция) | `fetch_product(article)` | как есть |

**Швы для тестов - два, и оба уже существуют по конструкции:**

1. **Транспорт WB** - `core.wbapi` принимает `httpx.AsyncClient` извне. В тестах подставляется фейк с записанными ответами. Через него проверяются все агенты целиком, без сети.
2. **Путь к базе** - `core.db` принимает путь. В тестах это временный файл. Через него проверяются доступ, счета, очередь и изоляция клиентов.

Чистые расчётные функции (формулы финансовой раскладки, пороги алертов, прогноз, скидки, банковские дни, контрольная сумма ИНН) тестируются напрямую, без швов - они не ходят никуда.
