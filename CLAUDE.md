# WBРентген (@WBRentgen_bot)

Telegram-бот для селлеров Wildberries: селлер подключает свой кабинет токеном WB и платит помодульно за аналитику. Бот сам ходит в WB Seller API, копит данные в SQLite и присылает разборы текстом и книгами Excel. Модули в `config.toml`: `finance` (990 ₽/мес), `rnp` (план-факт, 590 ₽/мес), пакет `all` (2290 ₽/мес); `ads` и `funnel` описаны, но скрыты (`visible = false`) до этапа 3.

## Команды

| Команда | Что делает |
|---|---|
| `pip install -r requirements.txt` | Зависимости. В текущем окружении уже установлены, заново гонять не нужно |
| `python bot.py` | Запуск бота (long polling). Нужен `.env` с `TELEGRAM_BOT_TOKEN`, иначе `SystemExit` с подсказкой |
| `python -m pytest -q` | Весь набор: 575 passed примерно за 25 секунд |
| `python -m pytest -q tests/test_finance.py` | Один файл |
| `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` | Новый `ENCRYPTION_KEY` |

Голого `pytest` в PATH нет, работает только `python -m pytest`. Python 3.13 (`.python-version`), хостинг Bothost запускает `Procfile`: `worker: python bot.py`.

## Ключевые файлы

- `bot.py` - только запуск: читает `.env`, зовёт `bot.app.startup()` и `build_app(token)`.
- `bot/app.py` - сборка приложения и фон. Порядок хендлеров: модули из `bot/handlers`, потом `/start` и `/help`, последним запасной обработчик текста из `legacy`. Очередь и расписание поднимаются в `post_init`, гасятся в `post_shutdown`. **Этот файл не трогают при добавлении команд.**
- `bot/handlers/__init__.py` - `register_all(app)` обходит пакет и зовёт у каждого модуля `register(app)`. Новая команда = новый файл с `register`.
- `core/config.py` - разбор `config.toml` и окружения: `settings()`, `modules()`, `price(module, months)`, `data_dir()`, `admin_ids()`, `seller_details()`.
- `core/db/__init__.py` - соединение, миграции, `repo(client_id)` и `admin_repo()`. Произвольного SQL наружу нет.
- `core/queue.py` - очередь задач в таблице `tasks`: `enqueue`, `register(kind, fn)`, `run_worker`, повторы по `[queue]`.
- `core/scheduler.py` - ежедневные и недельные работы, `tz()` как единственный источник часового пояса.
- `core/access.py` - `grant_access` и `revoke_access`, состояния `active/grace/off/paused/hidden`.
- `core/wbapi/client.py` - `HOSTS`, `ENDPOINTS`, `WBClient` с готовыми обёртками методов, `get_wb_client(client_id)`.
- `agents/finance.py` - агент 1, заполняет `fin_rows` и `fin_weeks`; на этих таблицах стоят агенты 2 и 3.
- `agents/lifecycle.py` - рассылки, продление, льготный период, удаление данных; связывает расписание, доступ и агентов.
- `migrations/001_initial.sql` - схема целиком, с комментариями про копейки и каскадное удаление.

## Архитектура

Четыре слоя, зависимости строго вниз: `bot` -> `agents` -> `core`. Исключение одно и названо в коде: `agents/lifecycle.py` знает про `agents.finance` и `agents.rnp`, поэтому и лежит в `agents`, а не в `core`.

Поток данных: хендлер принимает команду -> `core.queue.enqueue(...)` -> воркер вызывает обработчик задачи -> агент берёт `core.wbapi.get_wb_client(client_id)`, пишет результат в базу -> готовый отчёт уходит клиенту через `set_sender`/`set_delivery`. Отчёты (`finance.build`, `profit.build`, `rnp.daily`, `watchdog.check`) строятся **по базе и в WB не ходят**; в WB ходят только сборщики (`finance.collect`, `rnp.collect`, `profit.collect_ads`, `costs.build_template`).

Границы:

- **Работа с WB только через очередь.** Повторов внутри клиента WB нет, они живут в `[queue]`. Прямой вызов WB из хендлера при первой недоступности упадёт без повтора.
- **`core/wbapi` - единственное место с HTTP, хостами, версиями методов и токеном.** Агент получает клиент и зовёт обёртку; строку токена он не получит ниоткуда. Методов, меняющих что-либо в кабинете, не написано ни одного, и это единственная гарантия режима «только чтение».
- **Данные клиента только через `repo(client_id)`.** Сквозной срез по клиентской таблице в общем слое ровно один: `AdminRepo.tokens_with_exp()` для напоминаний о сроке токена, и он отдаёт только `client_id` и `exp`.
- **Доступ включается только `core.access.grant_access`** (счёт, ручная выдача, пробный период). Повтор с тем же `payment_ref` возвращает `Access.duplicate = True` и ничего не продлевает. Гасит только `revoke_access`, её идемпотентность стоит на состоянии, а не на `payment_ref`.
- **Платные команды обёрнуты `bot.handlers.tariffs.require_module(module)`**, своей проверки доступа хендлеры не пишут: без доступа клиент видит описание модуля, цену и кнопку «Оформить».
- **`core.clients.on_wb_error` - единственная реакция на ошибку WB:** 401 ставит модули на паузу, 403 не ставит.
- **Свои задачи и работы агент регистрирует сам** в `register_jobs()`, а зовёт её `register(app)` соответствующего хендлера (`finance`, `profit`, `rnp`, `dynamics`, `diagnostic`, `settings`). Виды задач: `finance_report`, `finance_collect`, `profit_report`, `rnp_collect_client`, `rnp_report_client`, `diagnostic`, `costs_template`, плюс имена работ расписания как виды задач.

Команды бота: `/start`, `/help`, `/connect`, `/disconnect`, `/tariffs`, `/modules`, `/trial`, `/finance`, `/profit`, `/dynamics`, `/rnp`, `/plan`, `/diagnostic`, `/costs`, `/settings`, `/paysupport`; владельцу `/stats`, `/acts`, `/grant`, `/revoke`, `/tasks`, `/diag`.

## Соглашения кода

- Деньги: в базе целые копейки, колонки с суффиксом `_kop`; в расчётах `Decimal`. `float` для денег не используется нигде, даже промежуточно. Проценты и доли остаются `REAL`.
- Любая функция слоя данных принимает `client_id` первым аргументом. Функции без `client_id` там не существует.
- Швов для тестов ровно два: транспорт WB (`http=` в функцию `core.*`, не в хендлер) и путь к базе (`path=None` в `register(app, *, path=None)` и в сами функции хендлера). Третий не заводить.
- Тексты бота только по-русски, **длинные тире запрещены** (`tests/test_texts_no_emdash.py` проходит по всем `.py`, `.toml`, `.sql`, `.env.example`, `.gitignore` и падает на длинном тире, среднем тире и горизонтальной черте). Документация `.md` в проверку не входит.
- Строки конкретного хендлера живут рядом с ним; `bot/texts.py` только для действительно общего.
- Читатель текстов - селлер, а не программист: «на складе осталось на 9 дней», а не `stock_days=9`.
- Числа-настройки (пороги, сроки, цены, частоты) берутся из `config.toml`, в коде их нет. Лимиты методов WB наоборот захардкожены в `LANES` (`core/wbapi/limits.py`): это факт про WB, а не настройка владельца.
- Новых миграций не пишут: схема целиком в `001_initial.sql`, а в `fin_rows` и `nm_daily` есть колонка `raw` с исходным JSON WB ровно для того, чтобы миграция не понадобилась.
- Новая переменная окружения обязательно добавляется в `.env.example` с пустым значением.
- Комментарии в этом проекте объясняют решение и его причину, а не пересказывают код. Держите тот же тон.

## Подводные камни

- **Четыре метода из исходного ТЗ Wildberries отключил в 2026 году.** Их путей нет в коде даже в комментариях, и тест падает, если такая строка появится. Что чем заменено - в `docs/wb-api.md`, единственный раз на весь проект.
- **Заголовок `Authorization: <токен>` без `Bearer`.** С `Bearer` Seller API не работает.
- **Без категории токена «Финансы» модуль `finance` не работает вообще**, и бесплатная диагностика тоже: отчёт о реализации переехал на `finance-api`. В исходном ТЗ этой категории не было.
- **Лимит отчёта о реализации 1 запрос в минуту** - самый жёсткий в проекте. Год выгружается страницами по `rrdId` и идёт долго, поэтому `/finance` только через очередь.
- **Комиссия по артикулу это тоже `vw`, и берётся она из `fin_rows.raw`**: отдельной колонки под неё в схеме нет. Строка без `raw` означает «комиссия неизвестна», такой артикул уходит в блок без прибыли. Подставлять соседнее `ppvzSalesCommission` нельзя, это другие деньги WB (`agents/profit.py`, `_articles_without_raw`).
- **Проценты в `/finance` и в `/dynamics` считаются по-разному, намеренно.** Агент 1 показывает готовые поля WB (тариф), сторож - фактически удержанную долю от выручки. Расхождение между ними и есть признак утечки, поэтому текст в `bot/handlers/dynamics.py` называет разницу прямо.
- **Обрезанные недели трактуются по-разному, тоже намеренно.** Сторож их в сравнение не берёт (была бы ложная тревога), прибыльность берёт и помечает (иначе селлер остался бы вообще без ответа).
- **Сбор данных идёт у всех подключённых кабинетов независимо от подписки.** Выключенная рассылка гасит только доставку: историю воронки WB отдаёт максимум за неделю назад, потерянное не вернуть.
- **`reportlab` не несёт кириллицы.** `core/billing/pdf.py` ищет системный TTF (DejaVu, Liberation, Noto, Arial); шрифта нет - счёт в базе создаётся, PDF не собирается, владелец получает подсказку. На боевом хосте проверяется один раз.
- **Админ-команда у чужого не отвечает ничем**: ни отказа, ни ошибки. Иначе перебор команд выдал бы список админки любому.
- **Группы хендлеров заняты:** `-100` ограничение частоты (`admin`), `-10` текстовый шаг диалога счёта (`billing`), `40` приём документов (`costs`), `50` кнопка «Оформить» (`tariffs`). Второй обработчик документов или второй диалог покупки вешать нельзя.
- **`sqlite3` и воркер очереди живут в одном процессе с ботом**; `data/` вне `DATA_DIR` на Bothost стирается при деплое.
- **`README.md` устарел**: он описывает первую версию бота и ссылается на `wb_api.py`, которого больше нет (код переехал в `legacy/card.py`). Верить нужно этому файлу и `docs/wb-api.md`.
- В корне лежат мусорные `wb-bot.zip` и `~$README.md`, оба вне git. Трогать их незачем.

## Финансовая раскладка: поля WB и формулы

Источник: `POST https://finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed`,
категория токена «Финансы», `period = weekly`. Метод из ТЗ
(`GET /api/v5/supplier/reportDetailByPeriod`) Wildberries отключил 15.07.2026,
старых имён полей в snake_case больше не существует. Лимит **1 запрос в минуту**,
самый жёсткий в проекте: длинные периоды выгружаются страницами по `rrdId` и
идут долго, поэтому `/finance` работает только через очередь.

Сверка: `POST /api/finance/v1/sales-reports/list` отдаёт готовые суммы по отчёту.

Параметр `fields` в запрос **не передаётся намеренно**: тогда WB отдаёт строку
целиком, и в колонке `fin_rows.raw` лежит вся строка, как обещано агентам 10
и 11. Таблица ниже это то, на чём стоит раскладка, а не фильтр запроса.

Неполная выгрузка помечается: если пагинация упёрлась в потолок страниц,
неделя записывается как неполная и клиент видит предупреждение. Неделя без
агрегата WB это «сверка не выполнена», а не «сошлось».

**Поля ответа, которые использует бот**

| Поле WB | Что значит | Куда идёт |
|---|---|---|
| `reportId` | номер отчёта, он же неделя | ключ `fin_weeks`, `fin_rows.report_id` |
| `rrdId` | номер строки и курсор пагинации | ключ строки в `fin_rows` |
| `dateFrom`, `dateTo` | границы отчётной недели | `fin_weeks.date_from`, `.date_to` |
| `docTypeName` | тип документа: продажа или возврат | делит продажи и возвраты |
| `retailAmount` | «Wildberries реализовал товар» | продажи и возвраты |
| `retailPriceWithDisc` | цена со скидкой | вес для средневзвешенных процентов |
| `forPay` | **к перечислению продавцу** | `for_pay_kop` |
| `vw` | вознаграждение Wildberries без НДС | комиссия в рублях |
| `commissionPercent`, `kvw` | размер кВВ и итоговый кВВ, % | комиссия в процентах |
| `acquiringFee`, `acquiringPercent` | эквайринг в рублях и процентах | как есть |
| `spp` | платформенные скидки, % | это и есть СПП |
| `deliveryService` | услуги по доставке покупателю | логистика |
| `paidStorage` | платное хранение | хранение |
| `paidAcceptance` | операции на приёмке | приёмка |
| `penalty` | общая сумма штрафов | штрафы |
| `deduction` | удержания, в том числе за рекламу | прочие удержания |
| `additionalPayment` | корректировка вознаграждения WB | отдельной статьёй |
| `nmId`, `vendorCode`, `subjectName` | артикул WB, артикул продавца, предмет | лист «По артикулам» |
| `quantity` | количество штук | продано и возвращено |
| `ppvzSalesCommission` | вознаграждение с продаж до вычета услуг поверенного | не используется: это **не** комиссия, подставлять вместо `vw` нельзя |

**Формулы**

Проценты не пересчитываются: у Wildberries есть готовые поля, и свой пересчёт
гарантированно разошёлся бы с личным кабинетом (R165).

- Продажи = сумма `retailAmount` по строкам, где `docTypeName` не «Возврат».
- Возвраты = сумма `retailAmount` по строкам возврата, отдельной статьёй.
- К перечислению = сумма `forPay` по всем строкам недели, включая возвраты.
- Комиссия WB, ₽ = сумма `vw`.
- Комиссия WB, % = средневзвешенное готового `commissionPercent`, вес `retailPriceWithDisc`. Проверка руками: `vw / retailPriceWithDisc * 100`.
- кВВ итоговый, % = средневзвешенное готового `kvw`.
- Эквайринг, ₽ = сумма `acquiringFee`; %  = средневзвешенное `acquiringPercent`. Проверка: `acquiringFee / retailPriceWithDisc * 100`.
- СПП, % = средневзвешенное готового `spp`.
- Логистика, хранение, приёмка, штрафы, прочие удержания, корректировка = суммы `deliveryService`, `paidStorage`, `paidAcceptance`, `penalty`, `deduction`, `additionalPayment`.
- Доля логистики, % = сумма `deliveryService` / сумма `retailAmount` * 100. Доля хранения считается так же по `paidStorage`. **Это наши определения, в документации WB таких формул нет.**
- Свод в месяц: неделя относится к месяцу, в котором она началась (`dateFrom`).
- Комиссия по артикулу = сумма `vw` по строкам этого артикула, включая возвраты, поднимается из `fin_rows.raw`; суммы по артикулам складываются в комиссию недели.
- Себестоимость в `/profit` = себестоимость за штуку * (продано минус возвращено): возвращённый товар вернулся на склад.
- Сверка: наша сумма по строкам минус готовая из `sales-reports/list` (`forPaySum`, `retailAmountSum`, `deliveryServiceSum`, `paidStorageSum`, `paidAcceptanceSum`, `penaltySum`, `deductionSum`). Расхождение больше рубля показывается клиенту, а не прячется.

Сторож скрытых расходов (`agents/watchdog.py`) считает те же пять показателей
иначе и осознанно: фактически удержанная доля от выручки недели (`vw` к выручке,
`acquiringFee` к выручке, доли логистики и хранения), кроме СПП, которая берётся
готовым полем. Пороги в `config.toml`, секция `[alerts]`, база сравнения - среднее
за `baseline_weeks` предыдущих полных недель.

Деньги в базе лежат целыми копейками (колонки с суффиксом `_kop`), в расчётах
`Decimal`, `float` для денег не используется нигде.

## Как здесь работает Autopilot

Сборка ведётся навыком `/autopilot`. Требования, спецификация и таски - в `.autopilot/`.
Прогресс - `.autopilot/dashboard.html`. Правило: требование из `manifest.md`
может снять только пользователь.

Если работа продолжается - скажи «продолжи автопилот»: состояние поднимется
из `.autopilot/state.js`, переспрашивать ничего не нужно.

Зависимость `tzdata` нужна не для красоты: на Windows системной базы часовых
поясов нет, и без неё `ZoneInfo("Europe/Moscow")` падает, а расписание уезжает
на UTC. Не выкидывайте её из `requirements.txt`.
