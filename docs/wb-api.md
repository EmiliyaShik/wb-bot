# WB Seller API: что используем и почему именно так

Сверено с официальной документацией dev.wildberries.ru 15.09.2026. Всё, что
в исходной сверке было помечено «НЕ ПОДТВЕРЖДЕНО», в код не попало и здесь
собрано отдельно, в последнем разделе.

Единственное место в проекте, которое ходит в WB, это `core/wbapi`. Агенты
получают клиент через `get_wb_client(client_id)` и вызывают готовые обёртки;
хостов, путей, версий и тем более токена они не знают.

---

## 1. Три метода из ТЗ отключены, используются замены

| Метод из ТЗ | Статус | Что вместо него |
|---|---|---|
| `GET /api/v5/supplier/reportDetailByPeriod` | отключён 15.07.2026 | `POST finance-api.wildberries.ru/api/finance/v1/sales-reports/detailed` |
| `GET /api/v1/supplier/stocks` | отключён 23.06.2026 | `POST seller-analytics-api.wildberries.ru/api/analytics/v1/stocks-report/wb-warehouses` |
| `POST /api/v2/nm-report/detail` | в текущей документации отсутствует | `POST seller-analytics-api.wildberries.ru/api/analytics/v3/sales-funnel/products` |
| `POST /adv/v2/fullstats` | в текущей документации отсутствует | `GET advert-api.wildberries.ru/adv/v3/fullstats` |

Старых путей нет в коде вообще, и это проверяется тестом
`test_disabled_wb_methods_are_absent_from_the_code`: он проходит по всем файлам
`core/` и `bot/` и падает, если такая строка где-то появилась.

Объявлены к отключению без даты: `GET /api/v1/supplier/orders` и
`GET /api/v1/supplier/sales`. Замена, когда понадобится, это лента заказов
`POST /api/analytics/v1/order-feed` (категория Аналитика). Сейчас не нужна.

## 2. Хосты и категории токена

| Что делает бот | Хост | Категория токена |
|---|---|---|
| Отчёт о реализации (агенты 1, 2, 3) | `finance-api.wildberries.ru` | Финансы |
| Воронка, остатки (агент 4) | `seller-analytics-api.wildberries.ru` | Аналитика |
| Расход рекламы (агенты 3, 4) | `advert-api.wildberries.ru` | Продвижение |
| Список карточек для шаблона себестоимости | `content-api.wildberries.ru` | Контент |
| Информация о продавце | `common-api.wildberries.ru` | любая |
| Ничего (остался для проверки связи) | `statistics-api.wildberries.ru` | Статистика |

Главное следствие: отчёт о реализации переехал на `finance-api`, а это другая
категория токена. **Без категории «Финансы» модуль `finance` не работает вообще.**
В исходном ТЗ этой категории не было.

Категория «Статистика» в текущей сборке не нужна ни для чего: оставшиеся там
методы объявлены к отключению, а их замена живёт в Аналитике.

## 3. Авторизация и разбор токена

Заголовок `Authorization: <токен>`, **без** `Bearer`. Префикс `Bearer`
относится к другому API Wildberries и с Seller API не работает.

Токен это валидный JWT со сроком 180 дней, и весь нужный смысл читается
из payload **без единого запроса к WB** (`verify_token(raw) -> TokenInfo`):

| Поле | Что значит |
|---|---|
| `id` | ID самого токена |
| `sid` | UUID продавца, он же ID кабинета |
| `exp` | Unix-время истечения |
| `s` | битовая маска свойств |
| `acc` | тип: 1 Базовый, 2 Тестовый, 3 Персональный, 4 Сервисный |
| `for` | `self` у Персонального, `asid:{ID}` у Сервисного |
| `t` | true у тестового токена (песочница) |

Биты маски `s`, счёт от нуля, проверка `s & (1 << бит)`:

| Бит | Категория | Бит | Категория |
|---|---|---|---|
| 1 | Контент | 11 | Возвраты покупателями |
| 2 | Аналитика | 12 | Документы |
| 3 | Цены и скидки | 13 | **Финансы** |
| 4 | Маркетплейс | 16 | Пользователи |
| 5 | Статистика | **30** | **Только на чтение** |
| 6 | Продвижение | | |
| 7 | Вопросы и отзывы | | |
| 9 | Чат с покупателями | | |
| 10 | Поставки | | |

Биты 0, 8, 14, 15 в официальной таблице отсутствуют, поэтому в коде их нет.

Один сетевой запрос при подключении делается только затем, чтобы убедиться,
что токен не отозван. Всё остальное о токене известно и так.

## 4. Методы, у которых есть обёртки

Больше обёрток никто не пишет. Ни одного метода, который что-то меняет
в кабинете, здесь нет и не будет: токен только на чтение.

| Обёртка | Метод WB | Дорожка лимита |
|---|---|---|
| `sales_report_detailed(date_from, date_to)` | `POST /api/finance/v1/sales-reports/detailed` | 1 запрос в минуту |
| `sales_reports_list(date_from, date_to)` | `POST /api/finance/v1/sales-reports/list` | та же, общая |
| `promotion_count()` | `GET /adv/v1/promotion/count` | 5 в секунду |
| `fullstats(ids, begin, end)` | `GET /adv/v3/fullstats` | 3 в минуту |
| `sales_funnel_products(start, end)` | `POST /api/analytics/v3/sales-funnel/products` | 3 в минуту |
| `sales_funnel_history(start, end)` | `POST /api/analytics/v3/sales-funnel/products/history` | 3 в минуту |
| `stocks_wb_warehouses()` | `POST /api/analytics/v1/stocks-report/wb-warehouses` | 3 в минуту |
| `cards_list()` | `POST /content/v2/get/cards/list` | 100 в минуту |
| `seller_info()` | `GET /api/v1/seller-info` | 1 в минуту |
| `probe_hosts()` | `GET /ping` на каждый домен | 3 запроса за 30 секунд на домен |

### Пагинация

- **Отчёт о реализации**: курсор `rrdId`. Первый запрос с `rrdId = 0`, дальше
  подставляется `rrdId` последней строки. Страницы кончились, когда вернулось
  меньше строк, чем просили. Кому нужно знать, обрезана ли выгрузка, зовёт
  `sales_report_detailed_paged()` и получает `ReportPages(rows, truncated,
  pages, last_rrd_id)`. `truncated` поднимается только когда кончился потолок
  страниц, а курсор остался живым: по длинам это не считается, последняя
  страница вполне может выйти ровно полной.
- **Карточки товаров**: курсор `updatedAt` плюс `nmID` из ответа переносится
  в следующий запрос. Повторять, пока `total` в ответе не станет меньше `limit`.
- **Аналитика (воронка, остатки)**: `limit` и `offset`.

### Разбиение по ограничениям WB

`fullstats` принимает максимум **50 кампаний** и **31 день** за запрос, поэтому
обёртка сама режет список кампаний и период. Агент об этом не думает.

### Поля, которые нужны боту

Отчёт о реализации (camelCase, старых snake_case из отключённого v5 больше нет):
`reportId`, `rrdId`, `dateFrom`, `dateTo`, `rrDate`, `nmId`, `vendorCode`,
`subjectName`, `docTypeName`, `sellerOperName`, `quantity`, `retailPrice`,
`retailAmount`, `retailPriceWithDisc`, `salePercent`, `spp` (это и есть СПП),
`commissionPercent`, `kvwBase`, `kvw`, `supRatingUp`, `isKgvpV2`, `vw`, `vwNds`,
`ppvzSalesCommission`, `ppvzReward`, `forPay`, `acquiringFee`, `acquiringPercent`,
`acquiringBank`, `deliveryAmount`, `returnAmount`, `deliveryService`,
`rebillLogisticCost`, `paidStorage`, `paidAcceptance`, `penalty`,
`additionalPayment`, `deduction`, `warehouseLogisticsCoeff`.

Денежные суммы приходят строками, парсить аккуратно.

Агрегаты `sales-reports/list`: `retailAmountSum`, `forPaySum`, `avgSalePercent`,
`deliveryServiceSum`, `paidStorageSum`, `paidAcceptanceSum`, `deductionSum`,
`penaltySum`, `additionalPaymentSum`, `bankPaymentSum`. Ими сверяется наш
расчёт с кабинетом: расхождение это повод показать предупреждение, а не молча
отдать свою цифру.

Реклама: расход на артикул за день это `days[].apps[].nms[].sum`, суммировать
по `apps`. Артикул здесь называется `nmId`; имя `nm` встречается только
в `boosterStats`. С июля 2026 суммы в валюте аккаунта, есть поле `currency`.

Воронка: `openCount`, `cartCount`, `orderCount`, `orderSum`, `buyoutCount`,
`buyoutSum`, `conversions{addToCartPercent, cartToOrderPercent, buyoutPercent}`.
**История доступна максимум за последнюю неделю**, поэтому суточные данные
забираются каждый день и копятся в `nm_daily`. Без этого динамика за месяц
не построится.

Остатки: `nmId`, `chrtId`, `warehouseId`, `warehouseName`, `quantity`,
`inWayToClient`, `inWayFromClient`. Поля `quantityFull` в новом методе нет,
ближайшее по смыслу это сумма трёх. С 15.08.2026 детализация по складам в РФ
временно скрыта (`warehouseId` приходит `-999999`), на расчёт остатка в днях
это не влияет.

Карточки: `nmID` (именно так, с заглавными буквами), `vendorCode`, `title`,
`subjectName`.

## 5. Лимиты

Алгоритм у WB это token bucket, и лимит считается **на их стороне по токену**,
а не по соединению. Значит два агента одного клиента делят один бюджет, и
в `core/wbapi/limits.py` корзина тоже одна на клиента.

| Дорожка | Лимит | Всплеск |
|---|---|---|
| Отчёт о реализации (`detailed` и `list` вместе) | 1 запрос в минуту | 1 |
| Информация о продавце | 1 запрос в минуту | 10 |
| Список кампаний | 5 запросов в секунду | 5 |
| Статистика рекламы | 3 запроса в минуту | 1 |
| Воронка продаж | 3 запроса в минуту | 3 |
| Остатки | 3 запроса в минуту | 1 |
| Карточки товаров | 100 запросов в минуту | 5 |
| `/ping` | 3 запроса за 30 секунд **на домен** | 3 |

Отчёт о реализации это отдельная медленная дорожка, и `detailed` с `list`
делят её намеренно: у обоих лимит 1 в минуту, а общая корзина гарантирует,
что вдвоём они не выйдут за него. Выгрузка года идёт страницами и долго.
Это не недостаток, это требование ТЗ: лучше медленнее, чем блокировка токена.

Лимит `/ping` берётся из `config.toml`, секция `[limits]`. Остальные лимиты
заданы в `core/wbapi/limits.py`, таблицей `LANES`.

### Заголовки ответа

| Заголовок | Когда | Что делает клиент |
|---|---|---|
| `X-Ratelimit-Remaining` | во всех ответах, кроме 429 | значение 0 опустошает корзину, и следующий запрос ждёт паузу, а не упирается вслепую |
| `X-Ratelimit-Retry` | при 429 | столько секунд и ждём, ровно столько |
| `X-Ratelimit-Limit`, `X-Ratelimit-Reset` | при 429 | справочно |

Если при 429 заголовка нет, пауза растёт сама. Числа для этого берутся из
`config.toml`, секция `[queue]` (`attempts`, `retry_base_sec`, `retry_factor`,
`retry_max_sec`) - той же, по которой повторяет задачи очередь. Своих чисел
у клиента WB нет.

**Повторов после 5xx и таймаута внутри клиента нет.** Их делает очередь, и
второй слой поверх неё перемножался бы с первым: одна пятисотка превращалась
бы в дюжину обращений к WB, что прямо противоречит требованию «лучше
медленнее, чем блокировка токена». Ожидание после 429 это не повтор, а
соблюдение лимита, поэтому оно остаётся здесь.

Соединение `httpx.AsyncClient` одно на процесс (`shared_session()`), закрывает
его `close_session()` при остановке бота. Новый клиент на каждый вызов означал
бы растущее число незакрытых пулов.

## 6. Ошибки: 401 и 403 это разные вещи

| Класс | Код | Что случилось | Что делает бот |
|---|---|---|---|
| `WBAuthError` | 401 | проблема с самим токеном: отозван, просрочен (180 дней), повреждён, сменился владелец кабинета | понятный текст про токен, модули на паузу, запись в журнал |
| `WBForbiddenError` | 403 | токен валиден, но прав не хватает: не та категория, метод недоступен этому типу токена, нет подписки Джем | **не пауза**: бот называет недостающую категорию и говорит, что перестало работать. Оплаченные дни идут дальше |
| `WBRateLimited` | 429 | слишком часто | ждём по заголовку и повторяем |
| `WBUnavailable` | 5xx, таймаут, обрыв | WB не отвечает | повтор с растущей паузой, потом понятное сообщение |
| `WBApiError` | прочее (400, 404) | повтором не лечится | в журнал |
| `WBTokenFormatError` | нет запроса | строка не похожа на JWT | просим прислать токен ещё раз |
| `WBTokenMissing` | нет запроса | кабинет не подключён | зовём на `/connect` |

Два формата тел ошибок: Problem Details (`application/problem+json`, с
`requestId`) и API Error (`application/json`, с `code`). Клиент достаёт из
тела `detail`, `title`, `message` или `code`, пропускает результат через
`core.audit.redact` и отдельно вычищает сам токен. **Токен не попадает ни
в логи, ни в сообщения, ни в тексты ошибок, даже обрезанным.**

Каждый вызов, удачный и неудачный, пишет строку в `api_calls`: клиент, хост,
метод, код ответа, время в миллисекундах.

## 7. Проверка связи и команда `/diag`

`GET https://<host>/ping` есть у каждого домена, ответ 200 это
`{"TS": "...", "Status": "OK"}`. Метод проверяет доставку запроса, валидность
токена и совпадение категории токена с сервисом. Работоспособность самого
сервиса он не проверяет.

**Документация прямо запрещает автоматизировать `/ping`**: при попытке запросы
временно блокируют. Поэтому:

- `/diag` запускается только вручную и только владельцем (`core.config.is_admin`);
- в расписание не ставится никогда, `job_queue` хендлер не трогает;
- между доменами пауза, повторов нет.

Как читаются ответы:

| Ответ | Что это значит |
|---|---|
| 200 | связь есть, запрос дошёл, токен принят |
| 401 | связь есть, запрос дошёл, но токен не принят. Дело в токене |
| 403 | связь есть, токен рабочий, но нет нужной категории для этого сервиса |
| 429 | связь есть, слишком часто. Лимит `/ping` 3 запроса за 30 секунд |
| 5xx | связь есть, ошибка на стороне WB |
| нет ответа, таймаут | запрос не дошёл или его оборвали. Так выглядит запрет по адресу или сети |

Проверка без токена тоже осмысленна: 401 в этом случае хорошая новость, он
означает, что запрос до Wildberries дошёл. Это и есть ответ на вопрос из ТЗ
про боевой хост и прокси.

## 8. Гео

В официальной документации нет ничего про ограничение доступа к API по стране
или IP: проверены страницы про лимиты, коды ошибок, FAQ и общее описание API.
Лимиты привязаны к аккаунту продавца и типу токена, а не к адресу. Утверждения
«нужен российский IP» в документации нет ни как подтверждения, ни как
опровержения, поэтому практическая проверка остаётся за `/diag` с боевого хоста.

## 9. Что осталось не подтверждённым

В коде на это ничего не опирается.

1. Поля payload `oid`, `sandbox`, `uid`: в документации их нет. Признак
   песочницы называется `t`. Числового ID продавца в токене нет, только UUID `sid`.
2. Назначение битов 0, 8, 14, 15 маски `s`.
3. Максимальная длина периода за один запрос в `sales-reports/detailed`.
   Пагинация по `rrdId` есть, поэтому выгрузка идёт страницами.
4. Точные даты отключения `adv/v2/fullstats` и старого отчёта воронки: методы
   отсутствуют, но записи об отключении не найдено.
5. Дата отключения `supplier/orders` и `supplier/sales`: объявлено, дата не названа.
6. Формулы финансовой раскладки: в документации WB их нет вообще. У всех
   ключевых величин есть готовые поля (`forPay`, `commissionPercent`,
   `acquiringPercent`, `spp`), и берутся именно они.
7. Соответствие старых имён новым (`delivery_rub` к `deliveryService`,
   `sa_name` к `vendorCode`) реконструировано по смыслу описаний.
8. Форма обёртки ответа у части методов (`data` или голый список), поэтому
   клиент понимает оба варианта.
