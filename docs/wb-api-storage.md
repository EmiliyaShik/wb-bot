# WB API: хранение, приёмка и удержания по артикулам

Разведка под один вопрос владельца: можно ли показать в отчёте о прибыльности
**хранение отдельным столбцом по каждому товару**, не выдумывая пропорцию.

Сверено с официальной документацией **dev.wildberries.ru 16.10.2026**, чтением
самой спецификации OpenAPI, которую портал отдаёт странице раздела «Отчёты».

Разделы 1-11 написаны по документации, до живых запросов: там, где сказано «в
документации не нашёл», в документации этого правда нет. **Раздел 12 добавлен
позже и написан по ответам настоящего кабинета**: он отвечает на часть
вопросов, которые разведка оставила открытыми.

Правило чтения то же, что в соседних файлах: если написано «в документации не
нашёл», значит его там правда нет, а не значит «наверное, так».

Приём обхода портала прежний: `dev.wildberries.ru` закрыт антиботом и на
обычное скачивание отдаёт 498. Читается настоящим браузером, а точные имена
полей берутся не из вёрстки, а из объекта `__redoc_state` со спецификацией
OpenAPI, который страница кладёт в свою разметку.

---

## 1. Короткий ответ

| Вопрос | Ответ |
|---|---|
| Есть ли отдельный отчёт о платном хранении | **Да.** `GET /api/v1/paid_storage`, отчёт с заданием и ожиданием готовности |
| Есть ли в нём артикул | **Да**, поле `nmId` |
| Есть ли дата | **Да**, поле `date`, разбивка посуточная |
| Есть ли сумма в рублях | **Да**, поле `warehousePrice`, «Сумма хранения» |
| Категория токена | **Аналитика.** У владельца она есть, новый токен не нужен |
| Сколько можно просить за раз | **8 дней** на один отчёт |
| Сойдётся ли с `paidStorage` отчёта о реализации | **В документации об этом не сказано ни слова.** Подробно в разделе 6 |
| Приёмка по артикулам | **Да**, `GET /api/v1/acceptance_report`, поля `nmID` и `total` |
| Удержания по артикулам | **Частично**: пять отдельных отчётов по конкретным причинам, общего отчёта под колонку `deduction` нет |

Главное в одну строку: столбец «Хранение» по каждому товару построить
**можно**, и это будут цифры Wildberries, а не наша пропорция. Но это цифры
**другого отчёта**, и совпадение с суммой `paidStorage` из отчёта о реализации
Wildberries нигде не обещает.

## 2. Отчёт о платном хранении

Хост у всех трёх методов один: **`seller-analytics-api.wildberries.ru`**
(в спецификации он проставлен каждому пути отдельно, полем `servers`).
Категория токена у всего раздела одна и названа в шапке: **Аналитика**.
Все три метода помечены в спецификации как читающие (`x-readonly-method: true`).

Лимиты ниже приведены для **персонального токена**: это тот тип, который
получает селлер в своём кабинете. У сервисного и базового с секретом здесь
те же числа, у голого базового жёстче.

### 2.1. Порядок вызова: три шага

Это отчёт с заданием, а не обычный запрос. Порядок написан в шапке раздела
документации дословно:

1. **Создать отчёт.** `GET /api/v1/paid_storage?dateFrom=...&dateTo=...`
   возвращает `data.taskId`.
2. **Дождаться готовности.** `GET /api/v1/paid_storage/tasks/{task_id}/status`
   возвращает `data.status`. Значения: `new` (новое), `processing`
   (обрабатывается), `done` (отчёт готов), `purged` (отчёт удалён),
   `canceled` (отклонено).
3. **Забрать отчёт.** `GET /api/v1/paid_storage/tasks/{task_id}/download`
   возвращает массив строк. Ответ `204` означает «нет данных», а не ошибку.

**Готовый отчёт хранится 2 часа**, после чего его нельзя будет получить. Это
прямая цитата документации, и это важно для очереди: задание, созданное и
забытое на три часа, придётся создавать заново.

Устройство один в один совпадает с остатками на складах
(`/api/v1/warehouse_remains`), которые в проекте уже знакомы: тот же хост, та
же категория токена, тот же порядок из трёх шагов, те же два часа хранения.

### 2.2. Создать отчёт

| | |
|---|---|
| Метод | `GET /api/v1/paid_storage` |
| Хост | `seller-analytics-api.wildberries.ru` |
| Категория токена | Аналитика |
| Лимит | 1 запрос в минуту, интервал 1 минута, всплеск 5 |
| Период за запрос | **максимум 8 дней** |
| Параметры | `dateFrom` и `dateTo`, оба обязательны, формат RFC3339 (`2019-06-20` или `2019-06-20T23:59:59`) |
| Ссылка | https://dev.wildberries.ru/docs/openapi/reports#tag/paidStorage/operation/getV1PaidStorage |

Ответ: `{"data": {"taskId": "219eaecf-e532-4bd8-9f15-8036ec1b042d"}}`.

Период длиннее восьми дней Wildberries отклоняет с кодом 400 и текстом
`Difference between dateFrom and dateTo should be less or equal 8 days`. Этот
пример ошибки лежит прямо в спецификации, то есть предел не догадка.

### 2.3. Проверить статус

| | |
|---|---|
| Метод | `GET /api/v1/paid_storage/tasks/{task_id}/status` |
| Лимит | 1 запрос в 5 секунд, интервал 5 секунд, всплеск 5 |
| Ссылка | https://dev.wildberries.ru/docs/openapi/reports#tag/paidStorage/operation/getV1PaidStorageTasksTaskIdStatus |

Ответ: `{"data": {"id": "...", "status": "done"}}`.

Сколько времени отчёт готовится, в документации не сказано.

### 2.4. Получить отчёт

| | |
|---|---|
| Метод | `GET /api/v1/paid_storage/tasks/{task_id}/download` |
| Лимит | 1 запрос в минуту, интервал 1 минута, всплеск 1 |
| Ответ 204 | нет данных |
| Ссылка | https://dev.wildberries.ru/docs/openapi/reports#tag/paidStorage/operation/getV1PaidStorageTasksTaskIdDownload |

### 2.5. Что в каждой строке отчёта

Имена и описания взяты из схемы `ResponsePaidStorage` спецификации, целиком,
ничего не придумано и ничего не пропущено.

| Поле | Тип | Что значит по документации |
|---|---|---|
| `date` | string | Дата, за которую был расчёт или перерасчёт |
| `originalDate` | string | Если был перерасчёт, это дата первоначального расчёта. Если перерасчёта не было, совпадает с `date` |
| `nmId` | integer | **Артикул WB** |
| `vendorCode` | string | Артикул продавца |
| `chrtId` | integer | ID размера для этого артикула WB |
| `size` | string | Размер (`techSize` в карточке товара) |
| `barcode` | string | Баркод |
| `subject` | string | Предмет |
| `brand` | string | Бренд |
| `giId` | integer | ID поставки |
| `warehousePrice` | number | **Сумма хранения** |
| `warehouseCoef` | number | Коэффициент хранения |
| `logWarehouseCoef` | number | Коэффициент логистики и хранения. На данный момент может быть только `0` |
| `volume` | number | Объём товара |
| `calcType` | string | Способ расчёта (в примере WB: `короба: без габаритов`) |
| `barcodesCount` | integer | Количество единиц товара (штук), подлежащих тарифицированию за расчётные сутки |
| `palletCount` | number | Количество паллет |
| `palletPlaceCode` | integer | Код паллетоместа. На данный момент может быть только `0` |
| `officeId` | integer | ID склада. На данный момент может быть только `0` |
| `warehouse` | string | Название склада. На данный момент может быть только `Склад WB РФ` |
| `loyaltyDiscount` | number | Скидка программы лояльности, ₽ |
| `tariffFixDate` | string | Дата фиксации тарифа |
| `tariffLowerDate` | string | Дата понижения тарифа |

Три поля (`officeId`, `warehouse`, `palletPlaceCode`) и ещё `logWarehouseCoef`
сейчас выродились в одно значение: Wildberries временно скрыл детализацию по
складам в РФ. Это та же история, что уже записана про остатки в
`docs/wb-api.md` (`warehouseId` приходит `-999999`). На столбец «Хранение по
товару» это не влияет: сумма и артикул на месте, пропадает только разрез по
складам.

Денежных полей в строке два, и это разные вещи: `warehousePrice` это сумма
хранения, `loyaltyDiscount` это скидка программы лояльности в рублях. **Входит
ли скидка в `warehousePrice` или вычитается из неё, в документации не
сказано.** Это надо проверить живым кабинетом до того, как число попадёт в
книгу.

### 2.6. Глубина истории и объём

- **Период за один отчёт: 8 дней.** Это единственное документированное
  ограничение периода.
- **Как глубоко можно уйти назад: в документации не нашёл.** У соседних
  отчётов такая оговорка есть прямым текстом («Данные доступны с августа
  2023», «Данные доступны с марта 2024», у отчёта о реализации «Данные
  доступны с 29 января 2024 года»). У платного хранения её нет вовсе.
  Проверяется только живым запросом.
- **Предела числа строк или размера ответа в документации нет.** У основных
  отчётов («Заказы», «Продажи») такое ограничение названо прямо (80000 строк),
  у платного хранения его нет. Это не значит «предела нет», это значит
  «не написано».
- **Фильтра по артикулу у метода нет.** Отчёт берётся на весь кабинет целиком.
  Строка это сутки плюс поставка плюс размер, поэтому у кабинета с большим
  ассортиментом строк за восемь дней будет много.

Арифметика, которая следует из лимитов, а не написана в документации: на одно
восьмидневное окно нужны создание (1 запрос в минуту) и скачивание (1 запрос
в минуту) плюс опросы статуса. То есть одно окно это примерно две минуты
машинного времени на кабинет, месяц хранения это четыре окна, примерно
восемь минут. Это сопоставимо с суточным сбором воронки и в ту же очередь
ложится без переделок.

## 3. Что нужно для столбца и какое поле это даёт

| Что нужно для столбца «Хранение, ₽» по товару | Какое поле это даёт | Откуда |
|---|---|---|
| Артикул, к которому относится расход | `nmId` | отчёт о платном хранении |
| Сумма хранения в рублях | `warehousePrice` | там же |
| День, за который начислено | `date` | там же |
| Был ли перерасчёт и за какой день изначально | `originalDate` | там же |
| Почему хранение такое: объём товара | `volume` | там же |
| Почему хранение такое: коэффициент склада | `warehouseCoef` | там же |
| Почему хранение такое: сколько штук тарифицировалось за сутки | `barcodesCount` | там же |
| Способ расчёта (короба, паллеты, с габаритами или без) | `calcType` | там же |
| Склад | `warehouse` (сейчас всегда `Склад WB РФ`) | там же |
| Скидка программы лояльности | `loyaltyDiscount` | там же, но см. оговорку в 2.5 |
| Название товара | **в этом отчёте нет** | `card_names`, как сейчас |
| Та же сумма хранения глазами отчёта о реализации | `paidStorage` | отчёт о реализации, **без `nmId`**, см. раздел 6 |

Хранения **на уровне артикула в самом отчёте о реализации нет и не появится**:
строки хранения приходят без `nmId`, и это подтверждено живым кабинетом
владельца. Отчёт о платном хранении это не замена той строке, а второй,
независимый источник тех же по смыслу денег.

## 4. Приёмка: отчёт есть, и он проще

| | |
|---|---|
| Создать отчёт | `GET /api/v1/acceptance_report?dateFrom=ГГГГ-ММ-ДД&dateTo=ГГГГ-ММ-ДД` |
| Проверить статус | `GET /api/v1/acceptance_report/tasks/{task_id}/status` |
| Получить отчёт | `GET /api/v1/acceptance_report/tasks/{task_id}/download` |
| Хост | `seller-analytics-api.wildberries.ru` |
| Категория токена | Аналитика |
| Период за запрос | **максимум 31 день** |
| Лимит на создание | 1 запрос в минуту, всплеск 1 |
| Лимит на статус | 1 запрос в 5 секунд, всплеск 1 |
| Лимит на скачивание | 1 запрос в минуту, всплеск 1 |
| Готовый отчёт хранится | 2 часа |
| Ссылка | https://dev.wildberries.ru/docs/openapi/reports#tag/acceptanceExpenses/operation/getV1AcceptanceReport |

Строка отчёта:

| Поле | Что значит |
|---|---|
| `nmID` | **Артикул WB** (здесь именно `nmID`, с заглавной `D`, а не `nmId`, как в хранении) |
| `total` | **Суммарная стоимость приёмки, ₽ с копейками** |
| `count` | Количество товаров, шт |
| `shkCreateDate` | Дата приёмки |
| `giCreateDate` | Дата создания поставки |
| `incomeId` | Номер поставки |
| `subjectName` | Предмет |

То есть приёмка по артикулам есть, и просить её можно сразу за месяц, а не за
восемь дней. Из всех трёх статей это самый дешёвый столбец.

Разница в написании имени артикула между двумя соседними отчётами (`nmId` в
хранении, `nmID` в приёмке) это не опечатка этого файла, а факт про WB. Та же
история уже была с `nmId` и `nm` в рекламе.

## 5. Удержания: пять отчётов по причинам, общего нет

Все пять живут на `seller-analytics-api.wildberries.ru`, все требуют категорию
токена **Аналитика**, у всех есть артикул.

| Что | Метод | Деньги | Артикул | Период и лимит |
|---|---|---|---|---|
| Занижение габаритов упаковки | `GET /api/analytics/v1/measurement-penalties` | `penaltyAmount` (сумма штрафа), `reversalAmount` (сумма сторно) | `nmId` | `dateTo` и `limit` обязательны, `dateFrom` и `offset` необязательны; 1 запрос в минуту |
| Замеры склада | `GET /api/analytics/v1/warehouse-measurements` | **денег нет**, только габариты | `nmId` | то же; 1 запрос в минуту |
| Подмены и неверные вложения | `GET /api/analytics/v1/deductions` | `bonusSumm` (сумма удержания), `bonusType` (причина) | `nmId` | `dateTo` и `limit` обязательны, есть `sort` и `order`; 1 запрос в минуту |
| Самовыкупы | `GET /api/v1/analytics/antifraud-details` | `sum` это **сумма заказа**, а не сумма удержания | `nmID` | необязательный `date`; данные с августа 2023; 1 запрос в 10 минут |
| Маркировка товара | `GET /api/v1/analytics/goods-labeling` | `amount` (сумма штрафа, руб) | `nmID` | `dateFrom` и `dateTo` обязательны, максимум 31 день; данные с марта 2024; 1 запрос в минуту |

Ссылки:

- https://dev.wildberries.ru/docs/openapi/reports#tag/retentionReports/operation/getV1MeasurementPenalties
- https://dev.wildberries.ru/docs/openapi/reports#tag/retentionReports/operation/getV1WarehouseMeasurements
- https://dev.wildberries.ru/docs/openapi/reports#tag/retentionReports/operation/getV1Deductions
- https://dev.wildberries.ru/docs/openapi/reports#tag/retentionReports/operation/getV1AnalyticsAntifraudDetails
- https://dev.wildberries.ru/docs/openapi/reports#tag/retentionReports/operation/getV1AnalyticsGoodsLabeling

Честная оговорка, и она важнее таблицы. В отчёте о реализации колонка
`deduction` называется просто «Удержания» и собирает в себя всё подряд,
включая удержания за рекламу. Пять отчётов выше покрывают **пять конкретных
причин**, и ни один из них не обещает, что вместе они дают всю колонку
`deduction`. **Отчёта «все удержания с разбивкой по товарам» в документации
нет.** Собрать колонку `deduction` из этих пяти значит построить число, про
полноту которого мы ничего не знаем.

У самовыкупов есть своя ловушка: поле `sum` описано как «Сумма заказа», а само
удержание по тексту документации составляет 30 процентов от стоимости товаров
при минимальной сумме всех удержаний 100 000 ₽. То есть числа удержания в
отчёте нет вовсе, есть только база, от которой оно считается. Подставлять
`sum` в колонку расходов нельзя.

## 6. Сойдётся ли с отчётом о реализации

Это главный вопрос, и честный ответ такой: **Wildberries нигде не обещает, что
сойдётся, и признаков того, что сойдётся, в документации нет.**

Что известно точно, по документации:

- В отчёте о реализации (`POST /api/finance/v1/sales-reports/detailed`,
  хост `finance-api.wildberries.ru`, категория токена **Финансы**) есть поле
  `paidStorage` с описанием ровно в одно слово: «Хранение». Там же
  `paidAcceptance` это «Операции на приёмке», `deduction` это «Удержания».
  Период отчёта недельный, строки привязаны к отчёту, а не к суткам.
- В отчёте о платном хранении (хост `seller-analytics-api.wildberries.ru`,
  категория токена **Аналитика**) сумма называется `warehousePrice`, «Сумма
  хранения», и привязана к суткам.
- Ни в описании одного метода, ни в описании другого **нет ни одной фразы о
  том, что эти суммы должны совпадать**, и нет ни одного общего ключа: ни
  `reportId`, ни `rrdId` в отчёте о хранении нет.

Что из документации следует как **причины расходиться**, и каждая названа
полем, а не догадкой:

1. **Перерасчёты.** У строки хранения есть `date` («дата, за которую был
   расчёт или перерасчёт») и `originalDate` («если был перерасчёт, это дата
   первоначального расчёта»). Значит, расход за первое число может приехать
   строкой, датированной позже. Сумма за календарные сутки, забранная сегодня,
   завтра может оказаться другой.
2. **Разные единицы времени.** Хранение считается по суткам, отчёт о
   реализации по неделям. Какие именно сутки попадают в какую неделю отчёта, в
   документации не сказано.
3. **Скидка лояльности.** В отчёте о хранении она отдельным полем
   (`loyaltyDiscount`), и неизвестно, вычтена ли она уже из `warehousePrice`.
   В отчёте о реализации у строки хранения такого поля рядом нет.
4. **Разные сервисы.** Один отчёт отдаёт `finance-api`, другой
   `seller-analytics-api`, у них разные категории токена и разные команды
   внутри Wildberries. Такое расхождение у нас уже есть: `sum` и `updSum` в
   рекламе это ровно тот же сюжет.

Вывод для продукта, и он жёсткий: **два числа под одним именем «Хранение» в
одном продукте хуже, чем одно число и пробел.** Если столбец по товарам
берётся из отчёта о платном хранении, а итог по кабинету из `paidStorage`
отчёта о реализации, то сумма столбца почти наверняка не сойдётся с итогом, и
селлер это увидит первым.

Два способа не врать, оба честные:

- **Назвать столбец своим именем.** Не «Хранение», а, например, «Хранение по
  данным отчёта WB о платном хранении», и рядом строкой показать, сколько
  хранения насчитал отчёт о реализации, с разницей между ними. Это ровно тот
  приём, который в проекте уже применён дважды: сверка `/finance` с агрегатом
  WB и две цифры расхода в `/ads`. Порог разговора там рубль.
- **Не класть новый столбец в тот же итог.** Столбец по товарам живёт сам по
  себе и в «Итого по кабинету» не складывается; в итоге по-прежнему стоит
  `paidStorage` из отчёта о реализации, то есть то число, которое селлер видит
  в своих взаиморасчётах.

Чего делать нельзя ни при каких условиях: молча заменить `paidStorage` в
финансовой раскладке суммой из отчёта о хранении. Отчёт о реализации это
документ взаиморасчётов, по нему селлер сверяется с Wildberries, и подмена
числа в нём сломает сверку, которая сейчас работает.

## 7. Чего нет или не нашёл

1. **Глубины истории платного хранения в документации нет.** Названо только
   ограничение периода на один отчёт (8 дней). У соседних отчётов дата начала
   данных указана прямо, здесь нет.
2. **Предела числа строк или размера ответа у платного хранения нет.** У
   основных отчётов он назван (80000 строк), здесь не назван.
3. **Сколько готовится задание, не сказано.** Есть только статусы и то, что
   готовый отчёт живёт 2 часа.
4. **Не сказано, вычтена ли `loyaltyDiscount` из `warehousePrice`.**
5. **Не сказано, как сутки хранения попадают в недельный отчёт о реализации**,
   и вообще не сказано, что суммы двух отчётов связаны.
6. **Фильтра по артикулу у отчёта о платном хранении нет.** Только период.
7. **Общего отчёта об удержаниях с разбивкой по товарам нет.** Есть пять
   отчётов по пяти конкретным причинам, и они заведомо не покрывают колонку
   `deduction` целиком (в неё входят, например, удержания за рекламу).
8. **Суммы удержания за самовыкупы в API нет**, есть только сумма заказа,
   от которой оно считается.
9. **Названия товара в отчёте о платном хранении нет.** Есть `subject`
   (предмет) и `vendorCode`, названия карточки нет.
10. **Ни одного другого метода с хранением по артикулам не нашёл.** Проверены
    целиком разделы «Отчёты» (24 метода) и «Аналитика и данные» (19 методов);
    среди типов отчётов «Аналитика продавца CSV» (`STOCK_HISTORY_REPORT_CSV`,
    `DETAIL_HISTORY_REPORT`, `GROUPED_HISTORY_REPORT` и три поисковых) хранения
    нет вовсе.
11. **Подтверждения живым кабинетом нет ни у чего из этого файла.**

## 8. Сойдётся ли это с нынешним устройством проекта

Коротко: ложится без ломки правил, но добавляет работы.

- **Категория токена уже есть.** Хранение, приёмка и удержания это всё
  «Аналитика», та же категория, на которой стоят воронка и остатки. Новый
  токен владельцу не нужен, и клиентам тоже.
- **Хост уже заведён**: `seller-analytics-api.wildberries.ru` живёт в
  `HOSTS["analytics"]`.
- **Нужны новые дорожки лимита** в `core/wbapi/limits.py`: у создания и
  скачивания 1 запрос в минуту, у статуса 1 запрос в 5 секунд. Под существующие
  дорожки они не подходят ни одна.
- **Нужен новый вид задачи в очереди.** Отчёт с заданием и ожиданием
  готовности в проекте встречается впервые: все нынешние методы отвечают
  сразу. Два часа жизни готового отчёта означают, что задание и скачивание
  должны уложиться в одно окно, а не растянуться по расписанию на сутки.
- **Нужна новая таблица под суточное хранение**, и миграций проект не пишет:
  схема целиком в `001_initial.sql`. Это отдельное решение, а не мелочь.
- **Сбор придётся вести ежедневно или хотя бы еженедельно.** Не из-за глубины
  (она неизвестна), а из-за восьмидневного окна и перерасчётов: догнать год
  задним числом это 46 окон, то есть больше полутора часов машинного времени
  на один кабинет.

## 9. Решения, которые нужны от владельца

Читателю этого раздела не нужно быть программистом. Каждый пункт это выбор, у
которого нет технически правильного ответа.

### 9.1. Берём ли хранение из второго отчёта вообще

Хорошая новость: отдельный отчёт о платном хранении у Wildberries есть, и в
нём по каждому товару и по каждому дню стоит сумма в рублях. Столбец будет
фактом Wildberries, а не нашей догадкой.

Плохая новость: это **другой отчёт**. Wildberries нигде не обещает, что сумма
в нём совпадёт с тем хранением, которое вы видите в еженедельном отчёте о
реализации и по которому с вами рассчитываются. Расхождение может быть, и
причины для него в самой документации названы: перерасчёты задним числом,
сутки против недель, скидка лояльности отдельной строкой.

**Вопрос: добавляем столбец, зная, что он может не сойтись с итогом?**

### 9.2. Как называть столбец и куда класть итог

Если столбец добавляем, то есть два честных пути:

- **Столбец рядом, итог прежний.** В строке каждого товара появляется
  «Хранение по данным отчёта WB о платном хранении», а в «Итого по кабинету»
  по-прежнему стоит хранение из отчёта о реализации. Под таблицей одной
  строкой: «по отчёту о хранении вышло столько-то, по отчёту о реализации
  столько-то, разница такая-то». Так уже сделано в сверке `/finance` и в двух
  цифрах расхода в `/ads`, и селлеры к этому привыкли.
- **Только столбец, без разговора о разнице.** Проще, но однажды селлер
  сложит столбец сам, не получит итог и спросит, какая цифра настоящая.

Рекомендация разведки: первый путь. Разница это не стыд, а польза: она
показывает перерасчёты, которых иначе не видно.

### 9.3. Что делать с «Расходами без артикула»

Сейчас хранение попадает в общую статью «Расходы без артикула» и разносится по
товарам пропорционально выручке. Если появляется настоящее хранение по
товарам, эти же деньги нельзя оставить и там, и там: они вычтутся дважды.

**Вопрос: убираем хранение из пропорции целиком, или оставляем как есть, а
новый столбец показываем справочно, не участвующим в прибыли?**

Первое честнее по смыслу, но меняет уже знакомые селлеру цифры прибыли.
Второе ничего не ломает, но даёт два числа про одно и то же в одной книге.

### 9.4. Приёмка

С приёмкой проще: отчёт есть, артикул есть, сумма есть, просить можно сразу за
месяц. Те же два вопроса (сойдётся ли с `paidAcceptance` и что делать с
пропорцией) стоят и здесь, но цена сбора втрое ниже.

**Вопрос: делаем приёмку вместе с хранением или отдельно и позже?**

### 9.5. Удержания

Отчёта «все удержания по товарам» у Wildberries нет. Есть пять отчётов по
конкретным причинам: занижение габаритов, подмены и неверные вложения,
самовыкупы, маркировка и замеры склада. Вместе они **не** дают колонку
«Удержания» из отчёта о реализации: туда входит и реклама, и многое другое.

**Вопрос: нужен ли селлеру разбор удержаний по причинам как отдельная вещь
(«вот за что с вас удержали»), не притворяющаяся разнесением колонки
`deduction` по товарам?**

Если да, это самостоятельный отчёт, а не столбец в книге прибыльности.

### 9.6. Сколько истории собирать и с какого дня

Глубина истории хранения в документации не названа, а окно одного запроса
восемь дней. Значит, догнать прошлое дорого, а потерянное может не
вернуться.

**Вопрос: начинаем копить с сегодняшнего дня у всех подключённых кабинетов
(как уже делается с воронкой и рекламой), или пробуем выгрузить историю назад
и смотрим, докуда отдаст?**

## 10. Попутная находка, не по теме разведки

В текущей спецификации отчёта о реализации
(`POST /api/finance/v1/sales-reports/detailed`) есть поле **`title`** с
описанием «Название товара». В `CLAUDE.md` и в `docs/wb-api.md` записано

названия держатся в таблице `card_names` и обновляются отдельным походом в

Проверять это живым кабинетом в эту разведку не входило, и трогать работающий
код по одной строке спецификации нельзя: поле может приходить пустым. Но
посмотреть стоит: если `title` приходит заполненным, отдельный поход в
`content-api` за названиями перестаёт быть нужным, а вместе с ним и категория
токена «Контент» у части клиентов.

Там же, в той же схеме, появились поля `officeName` (склад), `giId`
(ID поставки), `fixTariffDateFrom` и `fixTariffDateTo` (даты действия
фиксации тарифа), которых в нашем списке полей тоже нет.

## 12. Что подтвердил живой кабинет

Проверено на кабинете владельца (клиент 2) 16.10.2026, только чтение, на копии
базы. Боевая база при проверке не менялась.

**Отчёт о платном хранении работает ровно так, как описано выше.** Три шага,
`taskId` в ответе на создание, статус `done` после одного-двух `processing`,
скачивание массивом строк. За окно 01.10-08.10 пришло 449 строк, за сентябрь
по четырём окнам 30 суток без дыр.

**Поля строки совпали со спецификацией до буквы.** Пример живой строки:

```json
{"date": "2026-10-05", "originalDate": "2026-10-05", "nmId": 276174763,
 "vendorCode": "Арт. 15", "subject": "Карнавальные очки", "volume": 2.945,
 "calcType": "короба: товары свыше базы", "warehousePrice": 0.89528,
 "barcodesCount": 2, "loyaltyDiscount": 0, "warehouse": "Склад WB РФ",
 "warehouseCoef": 0, "logWarehouseCoef": 0, "officeId": 0,
 "palletPlaceCode": 0, "palletCount": 0, "tariffFixDate": "2025-12-08"}
```

**Сумма хранения точнее копейки.** `warehousePrice` приходит с пятью знаками
после запятой (`0.89528`), а строк за одни сутки по одному товару бывает
несколько: сутки плюс поставка плюс размер. Округлять каждую строку порознь
нельзя: на восьми сутках набегает рубля два, на годе под сотню. Поэтому сбор
складывает строки в `Decimal` и переводит в копейки один раз, на (сутки,
артикул).

**Суммы двух отчётов на закрытом месяце сошлись.** Сентябрь 2026:

| Что | Сумма |
|---|---|
| Отчёт о платном хранении, по товарам | 1 490,24 ₽ |
| Он же, по всем строкам собранных суток | 1 490,19 ₽ |
| `paidStorage` отчёта о реализации (строки с `rrDate` сентября) | 1 490,05 ₽ |
| Разница между столбцом и отчётом о реализации | **0,19 ₽** |

То есть на целом закрытом месяце два отчёта расходятся на копейки, и порог
разговора в рубль (тот же, что в сверке `/finance`) здесь молчит. Но на
незакрытом окне расхождение большое и законное: за 01.10-08.10 отчёт о
хранении дал 325,49 ₽, а `paidStorage` по строкам с теми же датами операций
164,80 ₽, потому что недели октября до отчёта о реализации ещё не дошли.
Поэтому правило «показывать оба числа и разницу» остаётся обязательным, а не
декоративным.

**Хранение по товарам за сентябрь** (оно и стоит теперь колонкой в книге):

| Артикул | Товар | Хранение, ₽ |
|---|---|---|
| 361482611 | Игрушка тоннель для кошек | 844,53 |
| 213884034 | Игрушка для кошек интерактивная мышка | 424,38 |
| 276174763 | Очки новогодние карнавальные | 111,62 |
| 335198749 | Интерактивная игрушка умная утка | 109,71 |

Разнесение по выручке, которое было до этого, давало совсем другую картину:
335198749 платил около 527 ₽ при настоящих 109,71 ₽, а 361482611 около 461 ₽
при настоящих 844,53 ₽. Прибыль первого была занижена на 418 ₽, второго
завышена на 383 ₽. Прибыль кабинета за сентябрь при этом поменялась только на
19 копеек (12 477,11 ₽ против 12 476,92 ₽): это та самая разница двух
источников, а не перераспределение.

**Отчёт о приёмке отвечает, а приёмки у кабинета нет.** За сентябрь задание
создалось, статус дошёл до `done`, отчёт вернулся пустым: ни одной строки.
Значит, живыми цифрами колонка приёмки не проверена, проверен только путь к
ней. Нулевая колонка в книге при этом правда нулевая, а не «нет данных».

**Скидка лояльности на этом кабинете нулевая во всех строках**, поэтому
вопрос «вычтена ли она из `warehousePrice`» живым ответом не закрыт. Поле
хранится рядом с суммой и в неё не вмешивается.

**Глубину истории живьём не мерили**: сбор идёт от сегодняшнего дня назад
окнами, и дно у него своё, не связанное с Wildberries, это самая ранняя
выгруженная неделя отчёта о реализации.
