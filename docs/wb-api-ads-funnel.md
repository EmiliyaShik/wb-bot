# WB API для модулей «Реклама» и «Воронка»

Справочник по методам, на которых стоят агент 5 (рекламный отчёт, модуль
`ads`) и агент 7 (диагност воронки, модуль `funnel`). Начинался как разведка
перед постройкой, сейчас оба модуля построены и продаются, поэтому рядом с
каждым методом сказано, какой обёрткой он вызывается.

Сверено с официальной документацией **dev.wildberries.ru 24.09.2026**, чтением
самой спецификации OpenAPI, которую отдаёт портал. Живых запросов к WB при
сверке не делалось: токен клиента не трогали, лимиты не жгли. Всё, что здесь
помечено как обёрнутое, проверено тестами проекта на фейковом транспорте, а не
живым кабинетом: это проверка нашей стороны договора, а не ответа Wildberries.

Что уже известно из прошлой разведки, здесь не повторяется. Авторизация,
разбор токена, битовая маска категорий, поведение при 401 и 403, заголовки
лимитов, `/ping` - всё это в `docs/wb-api.md`, и оно не изменилось.

Правило чтения: если написано «в документации не нашёл», значит его там правда
нет, а не значит «наверное, так».

## 1. Коротко: что подтвердилось, а что нет

| Из задания владельца | Что на самом деле |
|---|---|
| `/adv/v1/promotion/count` | **Жив**, версия v1, не менялся. Отдаёт только ID кампаний, сгруппированные по типу и статусу |
| `fullstats`, «сверить версии» | Живая версия **v3**: `GET /adv/v3/fullstats`. Версии v1 и v2 в текущей документации отсутствуют, в проекте уже используется v3 |
| ДРР по кампаниям и дням | Считается **внутри одного метода**: расход `sum` и выручка от рекламы `sum_price` лежат в одной и той же строке ответа. Сшивать два источника не нужно |
| Расход и заказы по дням и по кампаниям | Отдаётся **готовым разрезом**, складывать вручную не надо |
| CPO | Готового поля нет, это наше деление |
| Воронка: показы, переходы, корзина, заказ, выкуп | Четыре этапа из пяти есть. **Показов в воронке нет вообще**, ни в каком виде |
| Конверсии по этапам | Отдаются **готовыми полями**, считать не надо |
| Глубина истории воронки | Свод за период: **до 365 дней**. По дням: **максимум последняя неделя**. Подтверждено дословно |

Вывод в одну строку: модуль «Реклама» построен ровно как задумано, модуль
«Воронка» построен, но без первого этапа: показов у Wildberries нет, и пятым
этапом вместо них стоит видимость в поиске, названная своим именем.

## 2. Модуль «Реклама», агент 5

Все методы этого раздела живут на хосте **`advert-api.wildberries.ru`** и
требуют **категорию токена «Продвижение»** (бит 6 маски `s`). Так написано в
шапке каждого раздела документации по продвижению.

Общая оговорка WB про продвижение: данные синхронизируются с базой раз в
3 минуты, статусы кампаний меняются раз в минуту, ставки раз в 30 секунд.

Лимиты ниже приведены для **персонального токена**: это тот тип, который
получает селлер в своём кабинете (`acc = 3` в разборе токена). У базового
токена лимиты в разы жёстче, у сервисного совпадают с персональным.

### 2.1. Список кампаний

| | |
|---|---|
| Метод | `GET /adv/v1/promotion/count` |
| Хост | `advert-api.wildberries.ru` |
| Категория токена | Продвижение |
| Лимит | 5 запросов в секунду, интервал 200 мс, всплеск 5 |
| Параметров | нет |
| Ссылка | https://dev.wildberries.ru/openapi/promotion#tag/campaigns/operation/getV1PromotionCount |

Отдаёт `adverts[]`, где каждый элемент это группа «тип плюс статус»: поля
`type`, `status`, `count` и список `advert_list[]` с парами `advertId` и
`changeTime`. Плюс общее число кампаний в поле `all`.

Названий кампаний здесь нет, только номера. Тип `8` это устаревшая кампания с
единой ставкой, тип `9` это нынешняя кампания с единой или ручной ставкой.

В проекте обёртка уже есть: `promotion_count()` и `advert_ids()`.

### 2.2. Информация о кампаниях: названия и настройки

| | |
|---|---|
| Метод | `GET /api/advert/v2/adverts` |
| Хост | `advert-api.wildberries.ru` |
| Категория токена | Продвижение |
| Лимит | 5 запросов в секунду, интервал 200 мс, всплеск 5 |
| Ограничение объёма | параметр `ids`, максимум 50 кампаний за запрос |
| Ссылка | https://dev.wildberries.ru/openapi/promotion#tag/campaigns/operation/getV2Adverts |

Фильтры: `ids`, `statuses`, `payment_type` (`cpm` за показы или `cpc` за клик).

Отдаёт по каждой кампании: `id`, `settings.name` (**название кампании**),
`settings.payment_type`, `settings.placements`, `bid_type`, `status`,
`currency`, `nm_settings[]` со списком артикулов и ставками, а также
`timestamps` (создана, запущена, изменена, удалена).

**Это единственный подтверждённый способ узнать название кампании при её
номере.** В `fullstats` названия кампании нет, там только `advertId`. Второй
способ назвать кампанию это история затрат (пункт 2.4), но она даёт название
только у тех кампаний, по которым были списания.

Обёртка в проекте есть: `adverts_info(ids)`, режет список по 50 сама.
Названия оседают в `ad_campaigns`, но спрашиваются при каждом сборе по всем
кампаниям сразу, а не только по незнакомым номерам (так сделано в
`agents/ads.py`, функция `collect`). Причина: дорожка быстрая (5 запросов в
секунду, 50 кампаний за запрос), в том же ответе приезжает свежий статус
кампании, а название селлер может и переименовать. С названиями товаров в
`card_names` это не одно и то же: там дорожка дороже, и там есть срок
обновления `[cards] name_ttl_days`.

Статусы кампаний, одинаковые во всех методах: `-1` удалена, `4` готова к
запуску, `7` завершена, `8` отменена, `9` активна, `11` на паузе.

### 2.3. Статистика кампаний, главный метод отчёта

| | |
|---|---|
| Метод | `GET /adv/v3/fullstats` |
| Хост | `advert-api.wildberries.ru` |
| Категория токена | Продвижение |
| Лимит | 3 запроса в минуту, интервал 20 секунд, всплеск 1 |
| Кампаний за запрос | максимум **50** (`ids` через запятую) |
| Период за запрос | максимум **31 день** (`beginDate`, `endDate`, формат ГГГГ-ММ-ДД) |
| Только для кампаний в статусах | **7, 9 и 11** (завершена, активна, на паузе) |
| Ссылка | https://dev.wildberries.ru/openapi/promotion#tag/statistics/operation/getV3Fullstats |

Если период больше 31 дня, WB отвечает 400 с текстом про «max date range
31 days». В проекте резка по 50 кампаний и 31 дню уже сделана внутри обёртки
`fullstats(ids, begin, end)`, агент об этом не думает.

**Структура ответа, четыре уровня вложенности:**

```
[ кампания ]                       advertId, итоги за весь период
  └ days[]                         date, итоги за сутки
      └ apps[]                     appType: 1 сайт, 32 Android, 64 iOS
          └ nms[]                  nmId, name, итоги по артикулу
```

На каждом из четырёх уровней лежит один и тот же набор чисел: `views`,
`clicks`, `ctr`, `cpc`, `cr`, `atbs`, `orders`, `shks`, `canceled`, `sum`,
`sum_price`. Плюс на верхнем уровне `currency` (валюта аккаунта продавца,
ISO 4217) и `boosterStats[]` со средней позицией товара (`avg_position`,
`date`, `nm`) для кампаний с единой ставкой.

Обратите внимание: артикул называется `nmId` везде, кроме `boosterStats`, где
он называется просто `nm`. Это не опечатка WB, это так и есть.

### 2.4. История затрат: сколько с вас списали на самом деле

| | |
|---|---|
| Метод | `GET /adv/v1/upd` |
| Хост | `advert-api.wildberries.ru` |
| Категория токена | Продвижение |
| Лимит | 1 запрос в секунду, всплеск 5 |
| Период за запрос | минимум 1 день, максимум 31 день (`from`, `to`) |
| Ссылка | https://dev.wildberries.ru/openapi/promotion#tag/finances/operation/getV1Upd |

Отдаёт список списаний: `updNum` (номер документа), `updTime` (время
списания, бывает `null`), `updSum` (сумма), `advertId`, **`campName`**
(название кампании), `advertType`, `advertStatus` и `paymentType` (источник
денег: Баланс, Бонусы, Счёт, Кэшбэк).

Зачем он нужен отчёту: `sum` из `fullstats` это статистический расход, а
`updSum` это выставленная сумма. Они могут разойтись, и `paymentType` объясняет
почему: часть расхода могла уйти бонусами или кэшбэком, а не деньгами. Если
владелец хочет, чтобы цифра в отчёте сходилась с разделом «Финансы» рекламного
кабинета, брать надо `updSum`.

Это тот же приём, что уже применён в `/finance`: своя сумма по строкам плюс
готовый агрегат WB для сверки, и расхождение показывается, а не прячется.

Обёртка в проекте есть: `advert_upd(from, to)`. Списания оседают в `ad_upd`,
и `/ads` показывает обе цифры расхода, статистическую и фактически списанную,
с порогом разговора в рубль, как в финансовой сверке.

### 2.5. Поисковые кластеры, для агента минус-фраз

Модуль `ads` в `config.toml` объявляет второго агента, `minus_clusters`.
**Он не построен**: ни обёрток, ни кода под эти методы в проекте пока нет, и
`/ads` живёт без них. Раздел оставлен как готовая разведка на случай, когда
за него возьмутся. Что для него живо:

| Метод | Что даёт | Лимит | Объём |
|---|---|---|---|
| `POST /adv/v0/normquery/stats` | статистика по кластерам за период: `norm_query`, `views`, `clicks`, `atbs`, `orders`, `shks`, `ctr`, `cpc`, `cpm`, `avg_pos`, **`spend`** | 10 в минуту, всплеск 20 | до 100 пар «кампания плюс артикул» за запрос |
| `POST /adv/v1/normquery/stats` | то же самое, но с разбивкой по дням: `dailyStats[].date` плюс `stat` | 10 в минуту, всплеск 20 | до 100 пар за запрос |
| `POST /adv/v0/normquery/list` | активные и исключённые кластеры, по которым было не меньше 100 показов | 5 в секунду, всплеск 10 | по списку пар |
| `POST /adv/v0/normquery/get-minus` | нынешние минус-фразы кампаний | 5 в секунду, всплеск 10 | по списку пар |

Ссылки:
https://dev.wildberries.ru/openapi/promotion#tag/statistics/operation/postV0NormqueryStats и
https://dev.wildberries.ru/openapi/promotion#tag/statistics/operation/postV1NormqueryStats и
https://dev.wildberries.ru/openapi/promotion#tag/searchClusters/operation/postV0NormqueryGetMinus

Важная оговорка WB: у кампаний с оплатой за клик (`cpc`) поля `views`, `ctr` и
`cpm` приходят пустыми (`null`). Отчёт должен это переживать, а не делить на
пустоту.

Все четыре метода помечены в спецификации как читающие. Метод, который
**назначает** минус-фразы (`/adv/v0/normquery/set-minus`), в проекте не
появится: правило «ни одной обёртки, меняющей кабинет» действует и здесь.
Агент минус-фраз называет кластеры, которые жгут бюджет, а исключает их селлер
руками в своём кабинете.

| Отмены, штук | `canceled` | на всех четырёх уровнях |
| В корзину, штук | `atbs` | на всех четырёх уровнях |

### 2.7. ДРР: главный вопрос разведки

**Можно посчитать внутри одного метода.** Расход `sum` и выручка от рекламы
`sum_price` лежат в одной и той же строке ответа `fullstats`, на любом из
четырёх уровней. Сшивать два источника не требуется, и жёсткое правило проекта
про «число, собранное из другого поля» здесь не нарушается: это отношение двух
полей одного источника, а не подстановка соседа.

```
ДРР, % = sum / sum_price * 100
CPO, ₽ = sum / orders
```

Три честные оговорки, каждая важна:

1. **Готового поля ДРР у Wildberries нет.** В отличие от финансового отчёта,
   где комиссия и эквайринг приходят готовыми процентами, здесь процент наш.
   Значит, он может не совпасть с тем, что селлер видит в рекламном кабинете,
   и в тексте отчёта это стоит назвать прямо, как уже сделано в `/dynamics`.
2. **`sum_price` это выручка, которую WB приписал рекламе**, а не вся выручка
   артикула. В примере самой документации кампания со 139 кликами имеет
   `sum_price = 0`: заказов по рекламе не случилось, хотя товар в эти дни мог
   прекрасно продаваться сам. Селлеры под словом ДРР часто понимают другое:
   расход на рекламу, делённый на **всю** выручку артикула. Это уже два
   источника, и это продуктовое решение, а не техническое (см. раздел 5).
3. **Деление на ноль это обычное дело.** `sum_price = 0` при ненулевом
   расходе бывает часто. Отчёт должен говорить «заказов по рекламе не было,
   расход столько-то», а не рисовать бесконечность или прочерк.

### 2.8. Разрез по дням и кампаниям: готовый

Складывать вручную ничего не нужно. `fullstats` возвращает массив кампаний, у
каждой `days[]` по датам, у каждого дня `apps[]` по платформам, у каждой
платформы `nms[]` по артикулам. Всё уже посчитано на каждом уровне.

Единственное, что действительно надо складывать самим, это расход по артикулу
за день: он размазан по платформам, и `nms[].sum` нужно сложить по всем `apps`
за эту дату. В проекте это уже делает `agents/profit.py`.

### 2.9. Глубина истории рекламы

**В документации не нашёл.** У метода `fullstats` указан только предел на один
запрос (31 день) и отдельная оговорка про песочницу (там статистика доступна за
последние 30 дней). Ни слова про то, как глубоко можно уйти назад на боевом
хосте, в спецификации нет. У метода истории затрат `/adv/v1/upd` тоже сказано
лишь про максимум 31 день на запрос.

Чего в документации нет, но что следует из её же текста и стоит считать риском:
`fullstats` отдаёт данные только по кампаниям в статусах 7, 9 и 11. Кампания,
которую селлер удалил (статус `-1`) или отменил (статус `8`), из статистики
пропадает вместе со своей историей. Значит, копить расход у себя нужно по той
же причине, что и воронку: не потому, что WB обрежет по дате, а потому, что
кабинет может обрезать по статусу.

## 3. Модуль «Воронка», агент 7

Все методы живут на хосте **`seller-analytics-api.wildberries.ru`** и требуют
**категорию токена «Аналитика»** (бит 2 маски `s`). Подписка Джем для воронки
**не нужна**: в разделе «Воронка продаж» такой оговорки нет, в отличие от
соседних разделов, где она стоит прямым текстом.

### 3.1. Свод за период, с готовым сравнением

| | |
|---|---|
| Метод | `POST /api/analytics/v3/sales-funnel/products` |
| Хост | `seller-analytics-api.wildberries.ru` |
| Категория токена | Аналитика |
| Лимит | 3 запроса в минуту, интервал 20 секунд, всплеск 3 |
| Артикулов за запрос | `nmIds` от 0 до **1000**; пустой список значит «все товары» |
| Карточек в ответе | `limit` до 1000, по умолчанию 50; есть `offset` |
| Глубина истории | **максимум последние 365 дней** |
| Обновление данных | раз в час |
| Ссылка | https://dev.wildberries.ru/openapi/analytics#tag/salesFunnel/operation/postV3SalesFunnelProducts |

Тело запроса: `selectedPeriod` (обязательно, поля `start` и `end` в виде
ГГГГ-ММ-ДД), `pastPeriod` (необязательно, период для сравнения), `nmIds`,
`brandNames`, `subjectIds`, `tagIds`, `skipDeletedNm`, `orderBy`, `limit`,
`offset`.

Если указать несколько фильтров, вернутся карточки, подходящие под все сразу.
Если `pastPeriod` начинается раньше, чем год назад, WB сам подтянет его начало
к «сегодня минус 365 дней».

Ответ: `data.products[]`, у каждого элемента `product` (карточка) и `statistic`
с тремя блоками: `selected` (запрошенный период), `past` (период сравнения) и
`comparison` (динамика в процентах по каждому показателю). Блоки `past` и
`comparison` появляются, только если в запросе был `pastPeriod`.

**Сравнение с прошлым периодом и поиск просевшего этапа тут делать удобнее
всего: WB сам считает и прошлый период, и динамику.**

### 3.4. Что нужно отчёту и какое поле это даёт

| Этап воронки из задания | Поле в своде (`.../products`) | Поле в разрезе по дням (`.../products/history`) |

| Заказы, штук | `statistic.selected.orderCount` | `history[].orderCount` |
| Заказы, рублей | `statistic.selected.orderSum` | `history[].orderSum` |
| Выкупы, штук | `statistic.selected.buyoutCount` | `history[].buyoutCount` |
| Выкупы, рублей | `statistic.selected.buyoutSum` | `history[].buyoutSum` |
| Отмены и возвраты, штук | `statistic.selected.cancelCount` | поля нет |
| Отмены и возвраты, рублей | `statistic.selected.cancelSum` | поля нет |
| Отложенные | `statistic.selected.addToWishlist` | `history[].addToWishlistCount` |

**Готовые конверсии, считать самим не надо:**

| Конверсия | Поле в своде | Поле в разрезе по дням |
|---|---|---|
| Переход в корзину, % | `statistic.selected.conversions.addToCartPercent` | `history[].addToCartConversion` |
| Корзина в заказ, % | `statistic.selected.conversions.cartToOrderPercent` | `history[].cartToOrderConversion` |
| Заказ в выкуп, % | `statistic.selected.conversions.buyoutPercent` | `history[].buyoutPercent` |

Определения самой Wildberries: конверсия в корзину это доля посетителей,
открывших карточку и положивших товар в корзину; конверсия в заказ это доля
положивших в корзину и сделавших заказ; процент выкупа это доля заказавших,
которые товар выкупили, **без учёта товара, который ещё едет к покупателю**.

Все три конверсии приходят **целыми числами процентов**. Десятых долей в них
нет, и просадку на 0,4 процентного пункта по ним не увидеть. Это не повод
считать свои: своё деление разошлось бы с личным кабинетом, ровно как в
финансовом отчёте (правило R165 проекта).

**Динамика против прошлого периода тоже готовая**, в блоке
`statistic.comparison`: `openCountDynamic`, `cartCountDynamic`,
`orderCountDynamic`, `orderSumDynamic`, `buyoutCountDynamic`,
`buyoutSumDynamic`, `cancelCountDynamic`, `cancelSumDynamic`,
`avgPriceDynamic`, `shareOrderPercentDynamic`, `addToWishlistDynamic` и
вложенный блок `conversions` с конверсиями прошлого периода. Искать этап с
просадкой можно прямо по этим полям.

### 3.5. Две оговорки WB, которые ломают наивный расчёт

1. **Выкупы, отмены и возвраты записываются в день заказа, а не в день
   события.** Дословный пример документации: заказ 1 января, возврат 10 января,
   возврат появится в отчёте за 1 января. Значит, строка за вчера завтра может
   измениться, и `nm_daily` нужно перезаписывать окном, а не дописывать. В
   проекте это уже сделано: `agents/rnp.collect` забирает окно в неделю.
2. **Данные доезжают не мгновенно.** Большая часть заказов, переходов и
   добавлений в корзину появляется в течение часа, но малая часть может
   доезжать несколько дней. Отчёт за только что закончившийся день неточен по
   определению.

### 3.6. Глубина истории воронки: короткий ответ

- Свод за период (`/sales-funnel/products`): **365 дней**, с готовым сравнением
  с таким же прошлым периодом.
- По дням (`/sales-funnel/products/history`): **последняя неделя**, дословно.
- По дням, по группам (`/sales-funnel/grouped/history`): **последняя неделя**.
- По дням глубже недели: только CSV-отчёт `DETAIL_HISTORY_REPORT`, **и только
  с подпиской Джем**, до года назад.

Вывод для планирования не изменился и подтвердился: суточная воронка, которую
бот не забрал в течение недели, теряется навсегда. Собирать нужно каждый день
у всех подключённых кабинетов, независимо от того, оплачен ли модуль, и это
ровно то правило, которое уже записано в `CLAUDE.md`.

### 3.7. Сколько это стоит по времени

Тут есть неприятная арифметика, которую надо знать до постройки.

Метод «по дням» берёт **максимум 20 артикулов за запрос** при лимите
**3 запроса в минуту**. Значит:

| Артикулов у селлера | Запросов | Времени на один кабинет в сутки |
|---|---|---|
| 20 | 1 | 20 секунд |
| 100 | 5 | около 1,5 минут |
| 500 | 25 | около 8 минут |
| 2000 | 100 | около 33 минут |

Свод за период (`/sales-funnel/products`) берёт до 1000 артикулов за запрос и
в этом смысле дешевле, но суточного разреза не даёт вовсе.

Список артикулов, за которыми идти, брать неоткуда, кроме как из свода
(`/sales-funnel/products` с пустым `nmIds`) или из карточек товара. То есть
суточный сбор это сначала один запрос свода, потом пачка запросов истории.

## 4. Чего нет

Здесь собрано всё, что из задания владельца не подтвердилось или отсутствует.

### 4.1. Показов в воронке нет

Первый этап из задания, «показы в переходы», построить **нельзя**. Слова
«показы» нет ни в одном поле раздела «Воронка продаж»: проверены схемы
`Statistic`, `History`, `Conversions`, `Comparison` целиком, а также поиск по
всей спецификации аналитики. Первое, что знает Wildberries о покупателе, это
что он **уже открыл карточку** (`openCount`).

Что можно предложить взамен, по убыванию честности:

1. **Назвать воронку четырьмя этапами.** Переход в корзину, корзина в заказ,
   заказ в выкуп. Это ровно то, что WB показывает самому селлеру в его
   кабинете, и расхождений не будет. Самый дешёвый и самый честный вариант.
2. **Видимость вместо показов, при подписке Джем.** Метод
   `POST /api/v2/search-report/report` отдаёт `visibilityInfo.visibility`:
   это **вероятность в процентах**, что пользователь увидит карточку, и она
   зависит от средней позиции. Это **не количество показов**, и подменять одно
   другим нельзя. Плюс раздел «Поисковые запросы по вашим товарам» целиком
   доступен **только с подпиской Джем**, то есть модуль перестал бы работать у
   селлеров без неё.
   Ссылка: https://dev.wildberries.ru/openapi/analytics#tag/searchQueriesForYourItems/operation/postV2SearchReportReport

   Владелец выбрал оба варианта сразу (пункт 5.3), обёртка написана
   (`search_report`), дорожка лимита своя (`analytics-search`), а собранная
   видимость лежит в `funnel_visibility`.
   Подробности запроса, сверенные по самой спецификации: тело `MainRequest`
   требует пять полей, `currentPeriod`, `positionCluster`, `orderBy`, `limit`
   и `offset`; `pastPeriod` и `nmIds` необязательны. Лимит у персонального
   токена тот же, что у воронки: 3 запроса в минуту, интервал 20 секунд,
   всплеск 3. В ответе `data.groups[].items[]`, и у каждого товара лежат
   `nmId`, `name`, `visibility {current, dynamics}`, `openCard`, `addToCart`,
   `openToCart`, `orders`, `cartToOrder`, `avgPosition`. Видимости прошлого
   периода в ответе нет: есть только готовая динамика в процентах, и
   вычислять из неё «было» нельзя, потому что сама видимость приходит целым
   процентом.
3. **Показы рекламы из `fullstats` (`views`).** Это показы **рекламные**, и
   только у тех артикулов, которые сейчас в кампаниях. Органические показы
   туда не входят. Ставить это первым этапом воронки значит показать селлеру
   число, которое означает не то, что он подумает.

Рекомендация разведки была: вариант 1, вариант 2 надстройкой для тех, у кого
Джем уже есть. Владелец взял оба, и построено именно так: четыре этапа у всех,
пятый там, где Wildberries его отдаёт. Отказ поискового отчёта у кабинета без
Джема это нормальное состояние, а не авария, и отчёт говорит об этом спокойно.
Вариант 3 не взят и браться не должен.

### 4.2. Готового ДРР и CPO у Wildberries нет

Есть `cpc` (цена клика), `ctr` и `cr` (конверсия клика в заказ). Полей «ДРР» и
«CPO» нет ни в одном методе продвижения. Оба числа придётся считать самим, и в
тексте отчёта это надо назвать своими словами, как уже сделано в `/dynamics`
про расхождение процентов.

### 4.3. Названия кампании в статистике нет

`fullstats` знает только `advertId`. Название приходит либо из
`GET /api/advert/v2/adverts` (поле `settings.name`), либо из
`GET /adv/v1/upd` (поле `campName`, но только у кампаний со списаниями).

Это ровно та же история, что уже случилась с названиями товаров в финансовом
отчёте, и решается тем же приёмом: держать названия у себя, ходить за ними,
только когда появился незнакомый номер.

### 4.4. Кампании в статусах -1, 4 и 8 в статистику не попадают

`fullstats` работает только со статусами 7, 9 и 11. Удалённая кампания уносит
свою историю с собой. Это довод в пользу ежедневного сбора расхода, а не
выгрузки задним числом по запросу.

### 4.5. Глубина истории рекламы не документирована

Предела по глубине в документации нет ни у `fullstats`, ни у `/adv/v1/upd`:
названы только максимум 31 день на один запрос и отдельно оговорена песочница
(30 дней). Проверить это можно только живым запросом, а он в эту разведку не
входил.

### 4.6. Версий `fullstats` v1 и v2 в документации нет

Живая версия одна, третья. В текущей спецификации ни `/adv/v1/fullstats`, ни
`/adv/v2/fullstats` не встречаются. Записи об их отключении тоже не нашёл, но
и самих методов там больше нет, что совпадает с уже записанным в
`docs/wb-api.md`.

### 4.7. У кампаний с оплатой за клик половина полей пустая

В статистике поисковых кластеров (`normquery/stats`) для кампаний с типом
оплаты `cpc` поля `views`, `ctr` и `cpm` приходят `null`. Это написано в
документации прямым текстом. Агент минус-фраз должен это переживать.

### 5.1. Что мы называем словом «ДРР»

Два разных числа, оба имеют право на жизнь:

- **ДРР рекламы**: `sum` делить на `sum_price`. Считается внутри одного метода,
  совпадает с логикой рекламного кабинета, отвечает на вопрос «окупается ли
  сама реклама».
- **ДРР кабинета**: расход рекламы делить на **всю** выручку артикула (её даст
  либо `orderSum` из воронки, либо `retailAmount` из финансового отчёта). Это
  то, что чаще имеют в виду селлеры, но это сшивка двух источников, и цифра
  будет заметно меньше.

Целевой ДРР 15% из задания имеет смысл только вместе с ответом на этот вопрос:
15% от чего.

**Ответ владельца: обе, рядом и с подписью.** Вторая названа нашим расчётом.
Цель по ДРР сравнивается с первой, «ДРР рекламы»: именно она отвечает на
вопрос «окупается ли сама реклама». Без модуля «Финансы» второй цифры нет
вовсе, и на её месте стоит объяснение, а не число и не прочерк.

### 5.2. Где живёт целевой ДРР клиента

В задании сказано «по умолчанию 15%, меняется в `/settings`». По правилам
проекта числа-настройки живут в `config.toml`, а не в коде. Значит, 15% это
значение по умолчанию из `config.toml`, а личная цифра клиента ложится в его
настройки в базе.

**Ответ владельца: цель одна на кабинет.** Своя на каждый артикул честнее (у
ходового товара и у новинки разный нормальный ДРР), но требует экрана
настройки на каждый артикул, а это уже не одна кнопка. Сделано так: 15% это
значение по умолчанию из `config.toml`, секция `[ads]`, а личная цифра
клиента лежит в его настройках (`clients.settings`) и меняется в `/settings`.
Ноль и меньше возвращают к умолчанию.

### 5.3. Первый этап воронки: убрать или требовать Джем

Показов нет (пункт 4.1). Владелец ответил: **сделать оба варианта сразу.**

- Четыре этапа у всех: заход в карточку, корзина, заказ, выкуп. Всё на готовых
  полях, работает у любого селлера.
- Пятый этап там, где он доступен: видимость из поискового отчёта, подписка
  Джем. Он назван вероятностью в процентах, а не показами, и меряется своей
  меркой (готовая динамика WB в процентах, а не в процентных пунктах).
- Кабинет без Джема получает полноценный четырёхэтапный отчёт и спокойное
  объяснение, почему этапов четыре. Ни одного пугающего слова там нет, и это
  проверяется тестом.

### 5.4. Сколько артикулов собирать по дням

20 артикулов за запрос и 3 запроса в минуту (пункт 3.7). У селлера с двумя
тысячами артикулов суточный сбор занимает больше получаса машинного времени на
один кабинет.

Владелец ответил: **предел, и он в конфиге** (`[funnel] daily_articles = 200`,
самые оборотистые). Следствие названо клиенту прямо в отчёте: у медленного
товара состав меняется день ото дня, и в истории появляются пропуски. Товар с
пропусками показывается, но в сравнение не идёт, потому что меньше собранных
суток это меньше заходов, а не упавшая конверсия.

### 5.5. Какую цифру расхода считать правдой

`sum` из статистики или `updSum` из истории списаний (пункт 2.4). Они могут
разойтись, и `paymentType` показывает, что часть расхода могла уйти бонусами.

**Ответ владельца: обе, с прямым разговором о расхождении.** Это ближе к тому,
как уже устроен `/finance`, где расхождение с агрегатом WB показывается, а не
прячется. Порог разговора тот же: рубль.

### 5.6. Медиакампании: внутри модуля или снаружи

У WB Медиа (баннеры) отдельная статистика: `POST /adv/v1/stats` на хосте
`advert-media-api.wildberries.ru`, лимит 10 запросов в секунду, до 100
кампаний в теле запроса. В `fullstats` они не попадают.

**Вопрос владельцу: включать медиакампании в отчёт?** Ими пользуются немногие
селлеры, а стоит это отдельного хоста, отдельной обёртки и отдельного текста.

### 5.7. Объяснение через нейросеть

В задании агент 7 «опционально» объясняет просадку простым языком через Claude
Haiku с жёстким лимитом токенов. Это упирается не в WB, а в три вещи:

- расход на токены платит владелец, и он растёт с числом клиентов;
- в запрос уйдут данные кабинета клиента (артикулы, конверсии, суммы), то есть
  нужен новый пункт в оферте и, возможно, согласие клиента;
- новый ключ в окружении, а значит и новая строка в `.env.example`, и новое
  значение в списке `core.audit.redact`.

**Ответ владельца: не делаем.** Разбор идёт только по правилам. Типовая
подсказка без нейросети даёт девяносто процентов пользы и ничего из
перечисленного не требует: ни нового ключа в окружении, ни нового пункта в
оферте, ни данных кабинета, уезжающих наружу.

### 5.8. Цены модулей

**Ответ владельца получен, и модули открыты.** В `config.toml` стоят `finance`
990, `rnp` 590, `ads` 1290, `funnel` 490, все видимые. Порознь это 3360.
Пакет `all` открыт по цене 2490: дешевле на 870, то есть на 26 процентов.
Цену выбрал владелец из соображения, записанного прямо в `config.toml`: пакет
должен быть выгоднее, чем брать всё порознь, но не настолько, чтобы тот, кому
нужен один модуль, считал себя переплачивающим за отказ.

Следствие открытия пакета, которое стоило отдельной правки кода: слово `all`
стало именем продающегося модуля. В админской команде `/revoke` оно теперь
значит только пакет, а «погасить у клиента всё» пишется по-русски (`все`).

## 6. Попутная находка в текущем коде: починена

Находка была такая. Обёртка `sales_funnel_history()` в `core/wbapi/client.py`
клала `nmIds` в тело запроса **только если список передан**, а `agents/rnp.py`
в функции `collect()` звал её **без артикулов**. По спецификации
`POST /api/analytics/v3/sales-funnel/products/history` поле `nmIds`
обязательное, от 1 до 20 значений (схема `ItemHistoryRequest`,
`required: [selectedPeriod, nmIds]`, `minItems: 1`, `maxItems: 20`), то есть
запрос без него должен был получать 400 и суточная воронка не собиралась бы
вовсе. Оттуда же лишнее поле `skipDeletedNm`, которого в схеме этого метода
нет (оно есть у соседнего, сводного).

**Исправлено.** Теперь `nm_ids` у обёртки обязательный позиционный аргумент,
пустой список падает `ValueError` сразу и до сети (это ошибка зовущего, а не
пустой ответ Wildberries), больше двадцати артикулов режутся на пачки внутри
обёртки, а `skipDeletedNm` не отправляется. Кого собирать и сколько, решает
`agents/rnp.py` по `[funnel] daily_articles`: сначала самые оборотистые, по
выручке за то же окно.

## 7. Дорожки `LANES`: что заведено

Все числа для персонального токена. Дорожки живут в
`core/wbapi/limits.py`: это факт про Wildberries, а не настройка владельца,
поэтому они в коде, а не в `config.toml`.

| Метод | Дорожка | Лимит | Всплеск | Состояние |
|---|---|---|---|---|
| `GET /adv/v1/promotion/count` | `adv-count` | 5 в секунду | 5 | заведена |
| `GET /api/advert/v2/adverts` | `adv-adverts` | 5 в секунду | 5 | заведена |
| `GET /adv/v3/fullstats` | `adv-fullstats` | 3 в минуту | 1 | заведена |
| `GET /adv/v1/upd` | `adv-upd` | 1 в секунду | 5 | заведена |
| воронка, оба метода | `analytics-funnel` | 3 в минуту | 3 | заведена |
| поисковый отчёт (видимость) | `analytics-search` | 3 в минуту | 3 | заведена |
| `POST /adv/v0/normquery/stats` | `adv-normquery-stats` | 10 в минуту | 20 | нет, агент минус-фраз не построен |
| `POST /adv/v1/normquery/stats` | `adv-normquery-stats` | 10 в минуту | 20 | нет, там же |
| `POST /adv/v0/normquery/list` | `adv-normquery` | 5 в секунду | 10 | нет, там же |
| `POST /adv/v0/normquery/get-minus` | `adv-normquery` | 5 в секунду | 10 | нет, там же |
| `POST /api/analytics/v3/sales-funnel/grouped/history` | `analytics-funnel` | 3 в минуту | 3 | обёртки нет, метод не нужен |

Видимость получила свою дорожку, а не общую корзину с воронкой, намеренно:
Wildberries считает лимиты по методам, и общая корзина замедлила бы суточный
сбор воронки ради необязательного пятого этапа.

Неизвестная дорожка получает самый осторожный лимит (1 запрос в минуту), а не
свободу: ошибиться в сторону «медленнее» безопаснее, чем в сторону блокировки
токена клиента.

Отдельная оговорка из общего раздела про лимиты, которой в проекте пока нет
нигде: **один ответ с кодом 4XX может считаться за десять запросов**. В
документации это сказано на примере категории «Маркетплейс», но общая
формулировка звучит шире: «есть случаи, когда один запрос может быть равен
нескольким». То есть пачка ошибок опустошает корзину гораздо быстрее, чем
кажется по числу вызовов.
Ссылка: https://dev.wildberries.ru/openapi/api-information#tag/introduction/Limity-zaprosov
